# 示例：项目变更问题表闭环

## 场景

用户说：我是孙志强，腾讯文档里我名下待处理的问题帮我梳理。

目标不是只列出问题，而是逐条给出：属实/误报、根因、修复归属、验证结果，最后回写文档。

## 读取与筛选

PMS 固定维护两份文档，梳理时必须两份都查、全部 tab 都查：

- 读取 `config/issue_docs.json`，按配置里的 `file_id`、`tabs`、`header_row`、`responsibility_column`、`status_column`、`status_filter` 执行。
- 默认遍历全部 tab（含隐藏），责任列筛选 `match_person`（孙志强），状态列只取 `status_filter`（待处理）。
- URL 里的 `?tab=` 只是打开时定位，不是扫描范围。

步骤：

- 对两份文档分别 `sheet_get_sheet_info`，遍历配置里的全部子表（含隐藏）。
- 每个子表按配置的 `header_row` 定位表头，再按表头名称找责任列和状态列。
- `sheet_get_cell_data` 读取数据行，`return_csv=true`。
- 筛选责任列包含「孙志强」且状态为「待处理」的行；待验证/待解决/待确认/关闭/空状态一律跳过。
- 用户没有明确点名其他状态时，不把其他状态的行带进汇总。
- 汇总时标明文档 / 子表 / 行号；UAT1 隐藏副本按问题描述去重。

注意：如果用户昵称和表内姓名对不上，先用 AskUserQuestion 确认，不要猜。

## 逐条验证

对每条问题收集证据：

- 规格：Excel 逐格看 `cell.font.strike`，确认需求是否作废。
- 代码：codegraph 找 Controller/Service/前端组件，Grep 精确读关键行。
- 数据库：DBX 查 `t_node_field_permission` 的真实 `is_required / is_readonly / is_hidden / condition`。
- 单据数据：查 `t_wf_project_change` 对应表单号，确认字段实际值。

示例结论：

- 某条「退回后提示某字段必填」：后端节点保存取数未过滤 `condition`，配置里条件字段全被当成无条件必填；属实，后端 + 配置。
- 某条「项目编号应置灰」：前端输入框只绑了 `readonly`，没有 `:disabled`；属实，纯前端。
- 某条「区域展示」：配置已按节点控制，但前端门禁用错字段；部分属实。
- 某条「加签总裁条件」：字段权限已配，但“仅混合变更”逻辑未落地；需流程包或前端。
- 某条「人员自动带出」：接口已返回 `currentPersonnel / plannedSavingPersonnel / isPersonnelOptimization`，前端 `setProjectData` 未映射；前端。

## 修复与验证

- 后端：改取数口径，编译 + 定向单测。
- 配置：条件字段加 `condition='Y'`，保留 `is_required='Y'` 让前端可见时仍必填。
- E2E：拿现有单走详情 → `afterSave`（申请人提交）→ `complete`；确认 `current_node_id` 从 `T_Applicant` 流转到下一个节点。
- 部署：确认流水线成功；否则代码修复不生效。

## 回写备注

备注只追加，前缀是备注作者本人：

```text
这个项目是没有IT项目经理，不知道和这个有没有关系
孙志强2026-11-07：后端必填取数已统一（节点保存补齐 condition 分流），UAT/TEST 字段权限已对齐。
孙志强2026-11-09：E2E XMBG-202611-0040 申请人重新提交成功，已流转至主管节点，未再提示「变更后IT经理必填」。
```

责任人列如果是「常欢」，备注仍写「孙志强」——**责任人 ≠ 备注作者**。规则是「谁回复/谁操作，备注就署谁」；当前只有孙志强使用本技能，所以实际一律署「孙志强YYYY-MM-DD：」，将来别人操作时再改署实际操作人。

每条回复独立成行、各自带前缀：

```text
孙志强2026-11-07：后端必填取数已统一。
孙志强2026-11-09：E2E 复测通过，已流转至主管节点。
```

不要写成只在第一行署名、后面省略；也不要把署名改成责任人姓名。

## 回写责任人列

按 `tencent-docs-ops` 技能的人员列规则执行清空 → 写入 → 读回；本技能只决定是否改、改成谁。

## 示例：UAT「待业务复测」批量复测（2026-11-11）

用户说「有三个待业务复测的，先做 UAT E2E 验证，验证后改状态为待验证」。

- 范围识别：状态列仍是「待处理」，复测标记在备注末尾（「UAT 已部署…待业务复测」）；按备注筛出 3 条，与用户说的数量一致。只有根因分析、待流程配置的那条不算复测项，保持待处理。
- E2E 取证：用 `saveDraft/PM02007` 新建带标识的测试单据，先验证详情页流程标题；再用超限金额提交确认被拦截，用合规金额提交确认放行；字段权限接口和 `agent-browser` 页面双重确认审批节点按钮已隐藏、编制页按钮保留。
- 回写备注：每条验证结论都带 UAT、表单编号、期望 vs 实际、结论。

```text
孙志强2026-11-11：UAT E2E 验证通过。验证单据编号 GCXMCG-202611-0011；详情页流程标题为「陈金坤提交的工程项目采购需求GCXMCG-202611-0011」；提交后流转至「三级组织负责人」，标题保持一致。状态改为待验证。
孙志强2026-11-11：补充验证单据编号：GCXMCG-202611-0011。
```

- 状态回写：只把验证通过的 3 条改为「待验证」，未通过或未修复项保持「待处理」。
- 收尾：登记自建测试单的表单编号、实例 ID、当前节点；能终止实例则终止，不能终止则明确留给谁处理。

## 收尾

- 列出仍未闭环的项及归属（前端/后端/流程包）。
- 清理临时脚本、登录 token 缓存。
- 复核 git 工作区，不提交未授权改动。
- 用户确认后再改状态为「关闭」；关闭后该行即退出后续默认梳理范围。
