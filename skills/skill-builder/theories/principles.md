# Skill 设计核心原则

## 渐进式披露原则

**核心定义**：分层、按需加载知识与资源，避免一次性载入全部内容，解决 Token 爆炸与信息噪声问题。

**三层认知架构**：
- **目录层**：仅加载 `description`，用于全局语义匹配与触发判断
- **路由层**：激活后加载 SKILL.md，承担任务路由与流程指引
- **附录层**：仅在明确需要时加载 reference.md、examples.md 等附属资源

**内容拆分**：
- 高频核心语义内联于主文件，低频细节外置
- SKILL.md 遵循 **150 行上限**（≤150行内容直接写，>150行升级为纯路由）
- 确定性逻辑封装为脚本，降低推理与上下文开销

---

## 单一职责原则

**核心定义**：每个文件只负责一个明确的功能领域，避免职责混杂。

**文件职责划分**：
- **SKILL.md**：智能路由器，只负责路由和核心提示
- **reference.md**：详细规范，只负责规范说明
- **examples.md**：示例文档，只负责示例展示
- **theories/**：理论文件，只负责理论阐述
- **templates/**：模板文件，只负责模板定义

**判断标准**：
- ✅ 文件名准确反映内容、内容聚焦单一主题、修改原因唯一
- ❌ 文件名过于宽泛、内容涉及多个主题、修改原因多样

**反模式**：改一条规则要改 N 个文件 → 说明碎片化过度，应合并

---

## 依赖抽象原则

**核心定义**：技能依赖功能接口而非具体技能名称，调度系统基于功能匹配技能。

**❌ 违反（写死技能名称）**：
```yaml
# oracle-query SKILL.md
其他技能依赖此技能：
  - entity-client: 调用 oracle-query
```

**✅ 符合（依赖功能）**：
```yaml
# oracle-query SKILL.md
此技能提供的功能：
  - database-query：执行 SQL 查询，返回表格结果
```

**判断标准**：
- ✅ 技能声明"提供什么功能"，调用者请求"需要什么功能"
- ❌ 硬编码技能名称、环境变量默认值指向特定技能、硬编码技能路径

**反向依赖禁令（被依赖方不得引用依赖方）**：若技能 A 依赖技能 B（B 是被复用的底层/基础技能），则 B 不得引用 A，否则形成循环依赖，改动与触发都会互相牵连。

- ❌ 底层技能 B（如通用流程核心、基础规范）在其路由表 / 边界 / 正文中写 "→ `A` 技能""见 `A` 技能"，点名它的上层消费者
- ✅ 底层技能 B 只做能力化描述："由对应的领域 SOP / 项目规则负责"，不列举上层技能名
- 例外允许：B 引用它自己**向下**的通用工具（如 worktree / 评审工具），那些不是 B 的消费者，不构成环
- 检查方法：画出技能间引用关系图；任一 `A→B` 与 `B→A` 同时存在即为环 → 删除 `B→A` 的引用，改为能力化描述

## 自包含原则

**核心定义**：技能应尽可能自包含，小型脚本、执行文件、配置文件等依赖资源应打包在技能目录内，避免外部依赖导致技能不可移植或不可用。

**应包尽包清单**：
| 资源类型 | 示例 | 处理方式 |
|---------|------|---------|
| 脚本文件 | `.mjs`、`.sh`、`.py` | 放入技能目录或 `scripts/` 子目录 |
| 配置模板 | `.yaml`、`.json`、`.env` | 放入技能目录或 `templates/` 子目录 |
| 小型工具 | CLI 二进制、JAR 包 | 放入 `bin/` 子目录 |
| SQL/数据文件 | `.sql`、`.csv` | 放入技能目录或 `data/` 子目录 |

**判断标准**：
- ✅ 技能目录内包含所有运行所需文件，复制目录即可使用
- ✅ 外部依赖仅限于系统级工具（git、node、python 等已安装的运行时）
- ❌ 引用技能目录外的脚本路径（如 `C:\other\tool\script.sh`）
- ❌ 依赖其他技能的内部文件（应通过 Skill 工具调用，不直接读文件）
- ❌ 硬编码绝对路径引用外部资源

**目录结构扩展**：
```
.claude/skills/[skill-name]/
├── SKILL.md
├── reference.md
├── examples.md
├── scripts/          # 可执行脚本（新增）
├── bin/              # 小型工具/二进制（新增）
├── data/             # 数据文件（新增）
├── templates/        # 模板文件
└── theories/         # 理论文件
```

**与其他原则的关系**：
- 与**单一职责**互补：自包含不等于大杂烩，每个子目录仍有单一职责
- 与**依赖抽象**互补：自包含减少文件级依赖，依赖抽象减少技能级依赖
- 与**渐进式披露**兼容：scripts/bin/data 按需加载，不膨胀 SKILL.md

**最佳实践**：
- 创建技能时，检查所有引用的脚本/文件，能内包的内包
- 优化技能时，扫描外部路径引用，逐个评估是否应内包
- 体积过大的资源（>1MB）不内包，改为文档说明获取方式

## Single Source of Truth 原则

**核心定义**：所有规则定义集中在 reference.md，其他文件只引用不重复，避免"改一条规则要改 N 个文件"。

**文件职责划分**：
- **reference.md**：规则的**唯一定义处**（权威源）
- **examples.md**：只展示示例，规则细节链接到 reference.md
- **skill-test-checklist.md**：只列检查项，规则细节链接到 reference.md
- **templates/**：模板 + 注释指向 reference.md 对应章节

**判断标准**：
- ✅ 修改一条规则只需改 reference.md 一处
- ✅ 其他文件通过 `[reference.md - 章节名](./reference.md#锚点)` 引用
- ❌ 同一规则在多个文件中重复定义
- ❌ 改一条规则要改 N 个文件（反模式）

**文内 SSOT（同一文件内同样适用）**：约定值/规则在**单个文件内**也只允许定义一次，多处需要时用变量引用。来自真实技能审查的典型反模式与修复模式：

| 反模式 | 案例 | 修复模式 |
|--------|------|---------|
| 约定值硬编码多处 | worktree 路径在 SKILL.md 的约定行、建树示例、回收示例、多仓库段硬编码 4 处，改约定要动 4 处 | 文件开头设「单一事实来源」节定义变量（如 `$WT`/`$TREE`），其余全部引用变量 |
| 主文件抄细则 | SKILL.md 流程段把 reference.md 各阶段细则逐条抄一遍，末尾"硬约束"再抄第三遍 | SKILL.md 每阶段只留 1-2 行「动作 + 锚点跳转」；细则唯一正主在 reference.md；主文件只保留真红线（无法从细则推导的强制项） |
| 索引行抄规则正文 | 踩坑表「worktree 缺依赖」行把 junction/`.m2` 规则摘要抄一遍再加"见实施阶段" | 索引/路由表只写「场景 + 跳转」，不复述规则内容 |
| 过时硬编码值 | 启动端口写死 7153，多 worktree 并行时实际用 7154，文档失真 | 写弹性规则（"从 X 起，冲突时递增"）而非写死单值 |

**验证方法（改约定测试）**：模拟修改一条约定（如路径、端口、策略），数一下需要动的位置——**任何约定变更超过一处修改即为冗余**，按上表模式收敛到单一正主 + 引用。

**与其他原则的关系**：
- 是**单一职责**在文件间的延伸：reference.md 职责 = 规则定义，examples.md 职责 = 示例展示
- 与**渐进式披露**兼容：引用链接支持按需跳转，不强制加载全文
