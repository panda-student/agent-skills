# 迭代需求文档（PRD）标准结构

本文档描述归档器所期望的迭代需求文档格式，用于指导文档解析和切片提取。归档器可独立运行，不依赖 PRD 生成器，因此本文件自包含完整模板定义。

## YAML 头部（必需）

每个迭代需求文档必须以 YAML 头部开始，格式如下：

```yaml
---
name: {系统名称}-{模块/功能描述}-需求说明书-{迭代版本}
description: {迭代版本} 迭代需求文档
iteration: {迭代版本，如 v2.4}
date: {日期，YYYY-MM-DD}
depth: {Lite | Standard | Full}
modules:
  - {模块英文名1}
  - {模块英文名2}
deprecated_features:
  - {废弃的功能点ID1}
  - {废弃的功能点ID2}
---
```

**字段说明**：

| 字段 | 必需 | 格式 | 示例 |
|------|------|------|------|
| `name` | 是 | 格式 `{系统名称}-{模块/功能描述}-需求说明书-{迭代版本}`，与文档命名保持一致，支持中文 | `老师信息管理系统-老师信息管理-需求说明书-v1.0` |
| `description` | 是 | 格式 `{迭代版本} 迭代需求文档` | `v1.0 迭代需求文档` |
| `iteration` | 是 | 格式 `v{major}.{minor}` | `v1.0`、`v2.4` |
| `date` | 是 | `YYYY-MM-DD` | `2026-06-29` |
| `depth` | 是 | 深度策略，取值 `Lite` / `Standard` / `Full`，用于判断功能点要素完整性和合并策略 | `Standard` |
| `modules` | 是 | 字符串数组，必须与 3.3 节功能模块划分表中的"模块英文名称"列完全一致 | `["teacher"]` |
| `deprecated_features` | 否 | 废弃功能点 ID 列表，归档器读取此字段执行切片删除和索引清理。无废弃功能点时省略此字段 | `["F-SYS-003"]` |

## 文档结构

标准 PRD 文档包含以下章节：

### 1. 文档信息与修改记录
- 文档版本、作者、创建日期、审批人、审批日期
- 版本修改记录表

### 2. 产品概述
- 背景与机会、产品目标、目标用户
- 核心价值主张、产品范围 (In Scope / Out of Scope)、依赖说明

### 3. 核心流程与用户故事
- 核心业务流程图（Mermaid）
- 用户故事地图
- **功能模块与功能点划分表**（关键：用于归档器识别模块归属）

功能模块与功能点划分表格式：

| 模块 | 模块英文名称 | 功能点 ID | 功能点名称 | 功能类型 | 关联用户故事 | 简要说明 |
|------|-------------|----------|------------|----------|--------------|----------|

功能类型取值：新增 / 删除 / 编辑 / 查询 / 审批 / 导入导出 / 配置。

> **注意**：功能类型是对业务操作的分类（如"删除老师"是删除类型操作），不是功能点生命周期的增删标识。功能点的废弃/移除通过 YAML 头部 `deprecated_features` 字段声明。

### 4. 功能需求详述（核心：归档器主要提取此章节）

功能需求详述的结构如下：

```markdown
## 4. 功能需求详述

### 4.0 全局通用规则
交互规则、文案规范、异常统一处理。

### 4.x {模块中文名} ({模块英文名})

#### F-{模块大写}-{序号} {功能名称}
- **功能 ID**：F-{模块大写}-{序号}
- **关联用户故事**：US-xxx
- **功能描述**：一句话说明功能目的
- **前置条件**：使用该功能前必须满足的条件
- **后置条件**：功能执行后系统状态变化
- **主要流程**：编号步骤列表，描述正常操作路径
- **异常与分支流程**：异常情况的处理方式和提示
- **业务规则**：约束条件、校验规则、限制说明
- **子流程分组**（可选）：当功能点包含多个Tab/子操作时使用
- **页面交互说明**：UI布局、状态变化、操作反馈
- **页面字段说明**：

| 字段 | 字段英文名称 | 类型 | 必填 | 说明 |
|------|-------------|------|------|------|

- **EARS格式需求列表**：

| 需求ID | 需求描述 | EARS模式 |
|--------|----------|----------|
```

每个功能点包含 12 项要素（11 必需 + 1 可选）：

| # | 要素 | 必需 |
|---|------|------|
| 1 | 功能ID | ✓ |
| 2 | 关联用户故事 | ✓ |
| 3 | 功能描述 | ✓ |
| 4 | 前置条件 | ✓ |
| 5 | 后置条件 | ✓ |
| 6 | 主要流程 | ✓ |
| 7 | 异常与分支流程 | ✓ |
| 8 | 业务规则 | ✓ |
| 9 | 子流程分组 | ○ |
| 10 | 页面交互说明 | ✓ |
| 11 | 页面字段说明 | ✓ |
| 12 | EARS格式需求列表 | ✓ |

> **深度感知**：功能点要素数量根据 YAML `depth` 字段调整。Lite 深度仅含 5 项核心要素（功能ID、关联用户故事、功能描述、主要流程、EARS格式需求列表），Standard/Full 深度含完整 12 项要素。归档器合并策略据此判断功能点内容完整性。

EARS模式取值：事件驱动 / 条件异常 / 通用需求 / 状态驱动 / 可选特性 / 不需要。

### 5. 非功能性需求
- 性能要求、安全要求、兼容性要求、可用性要求

### 6. 数据埋点与统计（可选章节）
- 核心指标需求说明、埋点事件说明、数据报表需求说明

### 7. 验收与成功标准
- 功能验收标准（含关联功能点ID、预期结果）
- 指标验收标准（含关联非功能章节）

### 8. 假设与风险（可选章节）
- 关键假设、主要风险与应对

### 9. 附录（可选章节）
- 名词解释、参考文档、待确认事项

## 模块归属识别规则

归档器通过以下规则识别功能点的模块归属：

1. **功能点 ID 前缀（首选）**：功能点 ID 格式为 `F-{模块英文名大写}-{序号}`（如 `F-SYS-001`），其中 `F-` 为固定前缀，取 `F-` 之后、第二个 `-` 之前的部分转为全小写，即为模块英文名。例如 `F-SYS-001` → 模块 `sys`、`F-TEA-001` → 模块 `teacher`。
2. **小节标题兜底**：如果功能点 ID 无法提取模块前缀，回退到从章节标题中推断（如 `### 4.1 老师信息管理 (teacher)` → 模块 `teacher`）
3. **交叉验证**：提取的模块名与 YAML 头部的 `modules` 列表交叉验证，不匹配时给出警告

## 功能点提取边界

归档器按以下规则确定功能点的提取范围：

- **起点**：功能点标题，支持以下两种格式：
  - `#### F-{模块大写}-{序号} {功能名称}`（当前格式，如 `#### F-TEA-001 老师信息新增`）
  - `#### 4.X.Y 功能点 F-{模块大写}-{序号}：{功能名称}`（旧格式，如 `#### 4.1.1 功能点 F-SYS-001：手机号注册`）
- **终点**：下一个同级标题（`####`）或更高级标题（`###`、`##`）之前
- 提取的内容包括起点标题和直到终点之前的所有内容
- **识别方式**：以 `####` 级别标题中包含 `F-` 前缀的功能点 ID 为识别标志，不依赖固定标题格式
