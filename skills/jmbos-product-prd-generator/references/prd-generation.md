## YAML 元数据头部生成规则

### 输出路径规则

生成的PRD文档写入**项目迭代工作区目录**：`01.项目迭代工作区/{迭代标识}/1.产品/`

- **迭代标识**格式：`{YYYYMMDD}-{迭代名称}`，如 `20260604-定时任务与文件空间`
- **文件命名**：`{系统名称}-{模块描述}-需求说明书-{版本}.md`
- **索引文件**：与PRD文档同目录，固定命名 `索引.md`，每次输出PRD后自动生成或更新
- 归档到知识图谱由 prd-archiver skill 执行，generator 不越权写入归档目录

每个生成的 PRD 文档必须在最顶部包含 YAML 格式的元数据头部：

```yaml
---
name: {系统名称}-{模块/功能描述}-需求说明书-{迭代版本}
description: {迭代版本} 迭代需求文档
iteration: {迭代版本，如 v1.0}
date: {YYYY-MM-DD}
depth: {Lite | Standard | Full}
modules:
  - {模块英文名1}
  - {模块英文名2}
deprecated_features:
  - {废弃的功能点ID1}
  - {废弃的功能点ID2}
---
```

| 字段 | 必需 | 生成规则 |
|------|------|---------|
| `name` | 是 | 格式 `{系统名称}-{模块/功能描述}-需求说明书-{迭代版本}`，与文档命名保持一致，支持中文，如 `老师信息管理系统-老师信息管理-需求说明书-v1.0` |
| `description` | 是 | 格式 `{迭代版本} 迭代需求文档` |
| `iteration` | 是 | 格式 `v{major}.{minor}`，如 `v1.0`、`v2.4` |
| `date` | 是 | 当前日期，格式 `YYYY-MM-DD` |
| `modules` | 是 | 字符串数组，必须与第 3.3 节功能模块划分表中的"模块英文名称"列完全一致 |
| `depth` | 是 | 深度策略，取值 `Lite` / `Standard` / `Full`，与阶段一用户选择的深度策略一致。归档器通过此字段判断功能点要素完整性和合并策略 |
| `deprecated_features` | 否 | 字符串数组，声明本次迭代中废弃/移除的功能点 ID 列表（如 `["F-SYS-003"]`）。归档器读取此字段执行切片删除和索引清理。仅当用户明确要求移除某个已有功能点时填写，无废弃功能点时省略此字段 |

## 深度策略选择

### 深度等级定义

| 深度等级 | 名称 | 适用场景 | 生成内容 | 验证层级 |
|---------|------|---------|---------|---------|
| **精简版（Lite）** | 精简版 | 早期需求探索、快速原型讨论 | 章节 1-3 + 4.x 简要 | 仅 L1 |
| **标准版（Standard）** | 标准版 | 正常迭代需求、团队评审 | 必需章节 | L1 + L2 |
| **完整版（Full）** | 完整版 | 正式评审、跨团队协作 | 标准版 + 可选章节 | L1 + L2 + L3 |

### 深度选择规则

**核心原则：深度策略必须主动询问用户，不得自行默认。** 深度策略决定了文档的章节范围和功能点要素数量，对最终文档影响很大，用户应有权选择。

**询问方式**：向用户展示三种深度的对比说明，由用户选择：

```
请选择需求文档的深度策略：

| 深度 | 名称 | 生成内容 | 验证层级 | 适用场景 |
|------|------|---------|---------|---------|
| Lite | 精简版 | 章节 1-3 + 4.x 简要（5 项核心要素） | 仅 L1 | 早期需求探索、快速原型讨论 |
| Standard | 标准版 | 必需章节（1-5、7），功能点 12 项要素 | L1 + L2 | 正常迭代需求、团队评审 |
| Full | 完整版 | 标准版 + 可选章节（6-9） | L1 + L2 + L3 | 正式评审、跨团队协作 |

请选择：精简版 / 标准版 / 完整版
```

**自动判定规则**（仅当用户输入中已包含明确意图时适用，不替代主动询问）：

| 用户输入特征 | 自动判定深度 | 示例 |
|-------------|------------|------|
| 包含"草稿""简要""概述""快速"等词 | 精简版 | "快速生成注册功能草稿" |
| 包含"完整""正式""全要素""评审"等词 | 完整版 | "生成完整需求文档用于评审" |
| 用户明确指定深度 | 使用用户指定 | "用完整版深度生成 PRD" |
| 包含"优化""修改""调整"等调优动词 | 保持原文档深度 | "优化注册流程" |
| 无明确意图词 | **必须询问**，不得默认 | "生成 v2.6 的需求文档" |

### 各深度章节策略

**精简版（Lite）**：1-3 完整生成，4.x 仅概要（5 项核心要素），5-9 跳过

**标准版（Standard）**：1-4 完整生成，5 非功能性需求完整，6 跳过，7 验收标准完整，8-9 跳过

**完整版（Full）**：1-9 全部完整生成

### 精简版（Lite）深度功能点要素定义

精简版深度的功能点仅包含 **5 项核心要素**（对比标准版的 12 项），适用于早期需求探索与快速原型讨论：

| # | 要素 | 说明 |
|---|------|------|
| 1 | 功能ID | 格式 `F-{模块大写}-{序号}` |
| 2 | 关联用户故事 | 对应 3.2 节用户故事ID |
| 3 | 功能描述 | 一句话说明功能目的 |
| 4 | 主要流程 | 编号步骤列表，仅描述正常操作路径 |
| 5 | EARS格式需求列表 | 仅使用通用需求和事件驱动两种模式 |

精简版省略的要素：前置条件、后置条件、异常与分支流程、业务规则、子流程分组、页面交互说明、页面字段说明。

**精简版写法示例**见 [prd-template.md](prd-template.md)「精简版功能点写法示例」章节。

## 第2章 产品概述

- 背景与机会：业务场景、市场/用户痛点、为什么要做
- 产品目标：可量化的商业/体验目标
- 目标用户：用户画像概括（角色、特征、诉求），至少定义一个角色
- 核心价值主张：一句话说明产品核心价值
- 产品范围（In Scope）：本次包含的核心能力
- 明确的非范围（Out of Scope）：本次不做、防止自由发挥的内容
- 依赖说明：系统依赖、数据依赖、第三方依赖

## 第3章 核心流程与用户故事

- 核心业务流程图：使用mermaid语法，覆盖主流程和关键异常分支
- 用户故事地图：按史诗分组，每个用户故事包含ID、描述、优先级、验收标准概要
- 功能模块与功能点划分表：模块、模块英文名称、功能点ID（格式 `F-{模块英文名大写}-{序号}`）、功能点名称、功能类型（新增/删除/编辑/查询/审批/导入导出/配置）、关联用户故事、简要说明

## 功能模块划分原则

### 核心原则

1. **单一维度**：一个PRD内只能使用一种主划分维度（按角色/按流程阶段/按业务实体/按功能层级），禁止混合
2. **单一职责**：每个模块只负责一个明确的业务领域，能用一句话说清模块职责
3. **高内聚低耦合**：模块内功能紧密相关，模块间尽量减少依赖
4. **粒度适中**：每个模块包含2-8个功能点，整体通常3-8个模块

### 模块命名规范

| 要素 | 规则 | 示例 |
|------|------|------|
| 中文名称 | 2-6个汉字，结尾加"管理/配置/中心/工作台" | 用户管理、智能体工作台 |
| 英文名称 | 小写字母，单个单词或单词组合（无分隔符） | `user`、`workbench` |
| 功能点ID前缀 | `F-` + 模块英文名全大写 | `F-SYS-001`、`F-WRK-001` |

### 功能点粒度与ID复用

**功能点粒度**：共享同一UI入口或同一交互容器的多个子操作应合并为一个功能点（使用子流程分组）；具有独立入口或独立状态流转的子操作可拆分为独立功能点。

**功能点ID复用**：功能点ID代表一个用户操作入口+操作流程。只要入口和流程不变，只是字段/规则的增删改，就应复用已有ID。新增入口、新增流程或功能类型变化时新建ID。

**复用时的文档写法**：仅描述本次迭代的增量变更，不需要重写整个功能点。标注格式：

```
#### F-TEA-001 老师信息新增（v1.1 增强）

> 本功能点在 v1.0 基础上增强，仅描述 v1.1 变更内容。完整功能点描述见 v1.0 迭代文档。

**v1.1 变更内容**：
- 页面字段说明：新增紧急联系人姓名、紧急联系人关系、紧急联系人电话 3 个字段
- 业务规则：新增紧急联系人字段校验规则（见下方）
- EARS格式需求列表：新增 REQ-TEA-EC-ADD-001 ~ 006
```

### 跨模块引用标注

功能点的"后置条件"和"业务规则"中涉及跨模块引用时，必须使用结构化标注格式：

| 标注位置 | 格式 | 示例 |
|---------|------|------|
| 后置条件 | `→ 触发 [模块英文名] F-{模块大写}-{序号}` | `→ 触发 [change] F-CHG-001` |
| 业务规则 | `→ 引用 [模块英文名] F-{模块大写}-{序号}` | `→ 引用 [schedule] F-SCH-002 删除时级联` |

跨模块引用必须双向标注，仅标注直接引用，不标注间接依赖。

## 第4章 功能需求详述

- 全局通用规则：交互规则、文案规范、异常统一处理
- 使用mermaid语法创建业务流程图
- **EARS 语法分级应用**：按优先级分级使用 EARS 语法

### 功能点要素（与模板对齐）

每个功能点包含 12 项要素（11 必需 + 1 可选），完整写法示例见 [prd-template.md](prd-template.md) 末尾示例：

| # | 要素 | 说明 | 必需 |
|---|------|------|------|
| 1 | 功能ID | 格式 `F-{模块大写}-{序号}` | ✓ |
| 2 | 关联用户故事 | 对应第3.2节的用户故事ID | ✓ |
| 3 | 功能描述 | 一句话说明功能目的 | ✓ |
| 4 | 前置条件 | 使用该功能前必须满足的条件 | ✓ |
| 5 | 后置条件 | 功能执行后系统状态变化 | ✓ |
| 6 | 主要流程 | 编号步骤列表，描述正常操作路径 | ✓ |
| 7 | 异常与分支流程 | 异常情况的处理方式和提示 | ✓ |
| 8 | 业务规则 | 约束条件、校验规则、限制说明 | ✓ |
| 9 | 子流程分组 | 当功能点含多Tab/子操作时使用 | ○ |
| 10 | 页面交互说明 | UI布局、状态变化、操作反馈 | ✓ |
| 11 | 页面字段说明 | 表格：字段/英文名称/类型/必填/说明 | ✓ |
| 12 | EARS格式需求列表 | 表格：需求ID/需求描述/EARS模式 | ✓ |

> ✓ 必需 / ○ 可选（仅当功能点含多Tab/子操作时使用）

### 功能点要素自包含原则

功能点的核心要素（页面字段说明、异常与分支流程、EARS 需求列表）应保持自包含，读者不应被强制跳转到其他功能点。共享关系通过标注说明，差异点在条目内标注。

### 页面字段说明处理原则

页面字段说明应覆盖用户可见的所有关键字段，根据字段交互类型选择处理方式：

- **输入型字段**：用户需要输入或选择数据的字段，完整列出并标注必填性
- **展示型字段**：系统展示给用户查看、用户不可编辑的字段，完整列出，"必填"列填"-"，"类型"列标注"展示"
- **纯操作类（无字段）**：功能点既无输入字段也无展示字段，仅有操作按钮和交互反馈，写 `无数据字段，交互元素见页面交互说明`

> 判定关键：页面是否有用户可见的数据展示？有则必须列出展示字段，不可省略。

**页面字段说明的"说明"列**仅描述该字段独有的约束或行为，全局性规则（如回填行为、数据来源）归入业务规则中统一说明。

### 功能点索引表省略规则

当模块数 ≤ 3 且功能点总数 ≤ 10 时，4.x 功能点索引表可省略——3.3 功能模块划分表已提供足够的导航信息。仅当文档较长（多模块、多页滚动）时才需要索引表辅助定位。

## EARS 映射规则

EARS 语法分级（P0/P1/P2/P3）与对应 EARS 要求详见 [rules-engine.md R2.10「EARS 语法分级应用」](rules-engine.md#r210-ears-语法分级应用)。EARS 句式规范详见 [ears-syntax.md](ears-syntax.md)。

EARS 应描述**系统行为级别的需求**（"系统应当做什么"），而非"字段级约束"或"步骤级操作"。EARS列表必须覆盖以下三类来源，不可遗漏（验证规则对应 [rules-engine.md](rules-engine.md) R2.4.2-R2.4.4）：

| 来源 | 映射规则 | EARS模式 |
|------|---------|----------|
| **主要流程** | 按"**用户操作意图**"映射，每个意图至少对应1条EARS需求（一个意图可覆盖连续多个步骤） | 事件驱动 |
| **异常与分支流程** | 每个**独立异常/分支条件**对应1条EARS需求（不同触发条件或不同提示文案视为独立） | 条件异常 / 事件驱动 |
| **业务规则** | 仅**核心业务约束**对应1条EARS需求；字段长度、枚举取值、格式正则等非核心约束放入"页面字段说明"表"说明"列，不单独生成EARS | 通用需求 / 状态驱动 |

**核心业务约束判定**：
- ✅ 生成EARS：唯一性约束、跨字段约束、权限约束、状态流转约束
- ❌ 不生成EARS：字段长度、枚举取值、格式正则、必填性（这些约束在"页面字段说明"表的"说明"列中体现）

**生成顺序**：先从主要流程按操作意图生成EARS条目 → 再从异常与分支流程补充 → 最后从业务规则补充核心约束，确保三类来源全覆盖。

**子流程分组的EARS生成**：先为外层共用部分生成EARS条目，再按Tab顺序为各子流程生成，编号接续。

## 第5-9章内容指南

> 各章节字段表格与写法示例见 [prd-template.md](prd-template.md) 第5-9章对应章节。本节仅说明生成要点。

**第5章 非功能性需求：**
- 性能要求：页面加载（具体秒数）、接口响应（具体毫秒）、并发支持（具体人数）
- 安全要求：数据权限粒度、操作审计内容、敏感信息保护方式
- 兼容性要求：浏览器版本、客户端类型、分辨率范围、系统版本
- 可用性要求：可用性百分比、容错机制、备份周期

**第6章 数据埋点与统计：**
- 核心指标统计表：指标名称、计算口径、数据来源、业务目标/红线
- 埋点需求列表：事件ID、事件名称、触发时机、参数及取值逻辑
- 数据报表需求：报表名称、描述、关联指标ID（引用6.1）、更新频率；如不涉及报表可省略

**第7章 验收与成功标准：**
- 功能验收标准：使用 EARS 格式编写，覆盖所有 P0 功能，每个功能点 3-5 条验收条件
  - **与 4.x EARS 的区分**：4.x EARS 是需求定义（系统"应当做什么"，开发视角，细粒度）；7.1 验收标准是验收判定（"如何验证系统做对了"，测试/业务视角，聚焦关键场景）。验收标准从 4.x EARS 中提炼关键验收场景，不复制
  - **关联功能点ID**：每条验收标准必须关联到 4.x 的功能点ID，确保覆盖可追溯
  - **预期结果**：每条验收条件必须补充明确可观测的通过/失败判定标准
  - **验收方法**：不纳入 PRD 验收标准表，由测试团队根据验收条件自行制定测试方法
  - **埋点功能验收**（仅当文档包含第6章时）：埋点事件的触发时机和参数完整性属于 7.1 功能验收，关联功能点ID 指向第6章埋点事件ID
- 指标验收标准：与第5章非功能性需求对应
  - **关联非功能章节**：每条指标必须关联到 5.x 对应小节，确保可追溯
  - **埋点指标验收**（仅当文档包含第6章时）：由埋点数据计算的业务指标（如转化率、DAU）属于 7.2 指标验收，关联非功能章节指向第6章核心指标（6.1）

**第8章 假设与风险：**
- 关键假设：项目推进的前提条件
- 主要风险与应对：风险描述、影响程度、应对策略（可引用2.7节依赖项）

**第9章 附录：**
- 名词解释：业务术语和缩写
- 参考文档与设计灵感链接
- 待确认事项：开放问题、关联章节、责任人、截止日期、状态

## 特殊场景处理

| 场景类型 | 处理方式 |
|---------|---------|
| 多子系统复杂需求 | 拆分为多个独立PRD，每个子系统一个 |
| 既有系统改造 | 增加"现状分析"和"迁移计划"小节 |
| 实时性要求高 | 在性能需求中明确实时响应指标 |
| 涉及第三方系统 | 在依赖说明中明确对接规范和SLA |
| 移动端优先 | 兼容性需求调整优先级，标注端适配差异 |

## 生成检查点

每个章节生成后，引用 [rules-engine.md](rules-engine.md) 中的 **L1 快速规则** 进行即时校验。L1 规则涵盖：占位符、表格格式、标题层级、代码块、字段英文名称。

> 三层验证体系（L1/L2/L3）的完整定义详见 [rules-engine.md](rules-engine.md)。
