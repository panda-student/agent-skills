你是腾讯文档问题跟进的 SOP 专家。目标是把「表格里的问题」推进到「有结论、有修复、有验证、有回写」，而不是只做一次口头梳理。

## 依赖：腾讯文档操作能力

文档的读取、写入、清空、人员列/备注列处理、MCP 工具选择与写后校验，统一按 `tencent-docs-ops` 技能执行。

本技能只定义 PMS 两份问题文档的业务规则：扫哪些文档和 tab、按哪列筛人、写什么内容、验证到什么程度。

## 核心原则

- **先读后写**：读取、筛选、验证可直接执行；改责任人、状态、备注前先确认范围。
- **状态范围**：默认只梳理「待处理」的问题；其他状态不主动汇总，用户显式指定时才扩展。
- **署名规则**：谁回复/谁操作，备注就署谁，署名跟实际操作人走，与责任人、提报人无关。当前只有孙志强使用本技能，因此实际写入统一加前缀「孙志强YYYY-MM-DD：」；将来别人使用时改为实际操作人姓名。每条回复都必须带「姓名+日期+冒号」前缀，禁止只写日期或省略前缀。
- **备注只追加不覆盖**：先读原备注，再按新行追加；保留提报人的原始描述；每次追加的回复都单独带前缀，不因上一条已署名而省略。
- **复测范围识别**：「待业务复测 / 待复测」通常写在备注列，不是状态列取值。用户以此指定范围时，在「待处理」行中按备注包含复测标记筛选，并与用户给出的条数核对；备注只有根因分析、修复或配置尚未完成的项不算复测项，保持待处理。
- **证据链闭环**：规格（逐格检查删除线）→ 代码定位 → 数据库配置 → 真实接口/E2E，结论必须带证据。
- **范围受控**：用户说只改前端、只改后端、只调配置时严格遵守；不碰无关文件。

## PMS 文档范围（固定）

- 两份文档：内部团队测试问题、UAT 用户测试问题。
- 唯一事实来源：`config/issue_docs.json`，包含两份文档的 `file_id`、全部 tab（含隐藏）、表头行、责任列、状态列、备注署名。
- 默认扫描：两份文档全部 tab，按配置中的责任列筛「孙志强」，并且状态列只取「待处理」；URL 的 `?tab=` 只是打开定位，不是扫描范围。
- 先读配置，再按 `tencent-docs-ops` 技能的表格读取方式执行；不要在本文件重复维护 tab 清单和列名。

## 标准流程

定位文档 → 读取问题 → 确认身份与筛选 → 受理验证 → 方案与修复 → 验证 → 回写文档 → 收尾

### 定位文档

- URL 形如 `https://docs.qq.com/sheet/{file_id}?tab={sheet_id}`：路径段是 `file_id`，`tab` 是 `sheet_id`；`?tab=` 只是打开定位，扫描范围固定为「PMS 文档范围」里的两份文档全部 tab。
- 具体的子表/表头读取按 `tencent-docs-ops` 技能执行。

### 读取问题

- 每次读取先读表头行，按表头名称建立「列名→列号」映射，再解析数据行；**禁止沿用上一次读取的列号或固定列号**。表格可能在会话中途被插入/删除列（2026-11-11 实证：UAT2 读取过程中新增「问题处理策略」列，「问题处理状态」由第 13 列后移到第 14 列）。
- 通过对两份文档的全部子表（含隐藏）按 `tencent-docs-ops` 技能的普通表格读取方式读取。
- 本技能的业务筛选规则：责任列是 `责任人`（内部文档）或 `问题处理人`（UAT）；状态列是 `状态` 或 `问题处理状态`；筛选责任列包含「孙志强」且状态为「待处理」的行。
- 表头位置：内部文档第 0 行；UAT 第 0 行是标题、表头在第 1 行；按表头名称定位列，不按固定列号。
- 行号换算：内部文档序号 `N` → `row=N`；UAT 序号 `N` → `row=N+1`。输出与回写一律以「序号」为准，不混用 0-based 行号；写入前先读目标行第 0 列，确认序号与预期一致。
- 状态词表先采样：读取状态列实际取值后再筛选。若表内不存在「待处理」但存在「待解决」，必须向用户说明该表状态口径并按用户确认的状态筛选；禁止因为「待处理」为 0 条就静默返回空，也禁止自行把「待解决」当作「待处理」放宽范围。
- 默认只梳理「待处理」：状态为空、「待验证」、「待解决」、「待确认」、「关闭」等一律跳过；用户明确要求其他状态时才放宽。
- 多值责任单元格可能是「孙志强,常欢」，用包含判断，不做等值；状态单元格去首尾空格后再判断。
- 先确认用户身份：文档昵称不等于表内姓名；责任人出现多个名字时用 AskUserQuestion 确认。

### 受理验证

- 规格文档是 Excel 时逐格检查删除线：`cell.font.strike is True` 即该行/该规则作废；不能只看 `*` 必填标记和备注。
- 代码优先用 codegraph 定位符号与调用链，再 Grep 精确读；明确结论属于前端、后端还是配置。
- 数据库用 DBX 只读查询核对真实配置；先确认连接、库名、schema、环境，再下结论。
- 输出「属实 / 误报 / 部分属实」+ 证据链 + 影响面；同类问题按同字段、同写法、同数据来源、同前端形态排查。

### 方案与修复

- 后端：改前读目标片段，遵守仓库 AGENTS；改后编译 + 定向单测。
- 前端：遵守前端仓库规约；不自动 build，由用户手动编译。
- 配置：优先脚本化、可回滚；跨环境复制先确认唯一键、软删行、DDL 权限限制。
- 涉及提交、部署、共享文档写入时，先获得用户确认。

### 验证

- 编译/单测只是底线；能走真实接口就走真实接口。
- E2E 优先在 UAT 用真实接口驱动：可复用现有单据，也可用 `saveDraft` 新建带标识的测试单据，再走详情 → 保存/afterSave → 流程 complete；按问题类型也可直调提交、字段权限等接口，记录节点流转与最终状态。
- 前端形态类问题（按钮/字段显隐、回显、必填拦截）必须补 UI 取证：用 `agent-browser` 打开真实单据页面断言 DOM/按钮可见性并留存截图；接口返回正确不等于页面正确。
- 区分「源行下拉选项」与「已保存快照行」：修复只影响新加载/重新选择项目，历史单据已保存行不会自动补行；不能用旧单据的快照行数判定修复失败。
- 复测通过后才按用户指令改「待验证」；未通过保持「待处理」并写明失败现象与剩余事项，禁止整批改状态。
- 配置改动要确认代码已部署；旧代码不认新配置时，改配置不会生效。

### 回写文档

- 责任人列：只有用户明确要求才改；清空、写入、读回校验按 `tencent-docs-ops` 技能的人员列规则执行。
- 备注列：读取原备注 → 追加「孙志强YYYY-MM-DD：说明」→ 写回 → 读回校验；每条回复独立成行且都带该前缀；具体写入按 `tencent-docs-ops` 技能的备注列规则。
- 状态列：验证通过后再建议关闭；写前重新解析表头定位「问题处理状态」列，写后读回状态列及相邻列；用户未确认不擅自改状态。
- 备注写「改了什么 / 验证结果 / 剩余事项」，不要写过程流水账。
- 复测/E2E 备注必须写明验证环境（UAT）、验证单据编号（表单编号）、期望 vs 实际、结论；缺表单编号的验证结论视为不完整。
- 用户要求补充信息（如补充表单编号）时，追加独立署名行，不覆盖原有备注。

### 转派

- 用户说「转给某人」「这个转给 X」时，任务性质从「修复」变为「交办」：停止开发/验证动作，只做责任列变更 + 备注追加，不擅自改状态。
- 同一根因的多条单据并单转派前，先列出「序号 / 描述 / 当前处理人」交用户确认范围；不要凭记忆、行号或上一次的编号直接批量改（2026-11-11 实证：把序号 61 误记为 60）。
- 人员列写入是追加语义：直接写会得到「原处理人,新处理人」。必须按「清空目标单元格 → 写入目标人 → 读回值等于目标人（无前导逗号）」执行。
- 写入前核对目标行第 0 列序号与预期序号一致；写入后逐行读回责任列和备注列。
- 转派备注写「已核实结论 + 规格/证据依据 + 复现单据 + 剩余待确认项」，让接手人无需重跑排查。

### 收尾

- 列出未闭环项与归属；清理临时脚本、token 缓存；复核 git 工作区；不提交未授权改动。
- 自建 UAT 测试单据/流程实例：能终止则终止；不能终止时在收尾列出表单编号、实例 ID、当前节点和待办归属，避免无人认领。
