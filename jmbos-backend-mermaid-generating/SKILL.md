# Mermaid 图表生成器

## 这个 Skill 干嘛用？

把一段文字、一个概念、一套流程，变成可视化的 Mermaid 图表代码。

你说需求，我帮你画图。不用操心语法，自动避开常见坑。

**默认设置：**
- 垂直布局（TB），除非用户要求水平
- 标准详细度（简洁与信息量的平衡）
- 专业配色方案，语义化用色
- 兼容 Obsidian / GitHub 语法

## 支持哪些图？

| 图表类型 | 什么时候用 |
|---------|-----------|
| **流程图** (graph TB/LR) | 有步骤、有顺序的事，比如业务流程、决策树 |
| **架构图** (graph TB + 分层子图) | 系统结构、技术栈、模块关系，强调分层和组件 |
| **时序图** (sequenceDiagram) | 多个角色之间交互，比如 API 调用、系统交互、消息流 |
| **状态图** (stateDiagram-v2) | 状态变来变去的事，比如订单状态、审批流程、生命周期 |
| **思维导图** (mindmap) | 有层级的内容，比如知识体系、功能模块、主题拆解 |
| **循环图** (graph + 循环布局) | 有反馈、有循环的事，比如迭代流程、持续改进、Agent 反馈系统 |
| **对比图** (graph + 并行路径) | 两边对比，比如方案对比、前后对比、传统 vs 现代 |
| **ER图** (erDiagram) | 数据库表结构和实体关系，表与表之间的关联 |
| **甘特图** (gantt) | 项目时间安排、任务进度、里程碑管理，适合展示开发计划 |
| **饼图** (pie) | 占比分析、构成展示，如预算分配、市场份额、用户构成 |
| **类图** (classDiagram) | 面向对象设计、系统类结构、设计模式说明 |

## 模糊提问处理（必须反问）

当用户请求信息不完整或模糊时，**必须反问用户**，不能猜测生成。

### 必须反问的场景

| 场景 | 用户输入示例 | 反问方式 |
|------|-------------|---------|
| **未指定图表类型** | "帮我画个图" | "你需要画什么类型的图？支持流程图、架构图、时序图、状态图、思维导图、ER图、甘特图、饼图、类图等。" |
| **可做多种图** | "画一个用户下单" | "可以做流程图展示下单步骤，也可以做时序图展示系统交互，你想看哪种？" |
| **缺少关键内容** | "画个登录流程" | "请描述登录的具体步骤：1. 用户输入什么？2. 校验哪些信息？3. 有哪些分支（成功/失败）？" |
| **描述过于笼统** | "画个电商系统架构" | "需要包含哪些模块？（如：用户端、商品服务、订单服务、支付服务、库存服务等）" |
| **ER图缺少表结构** | "画个用户和订单的ER图" | "请提供表的字段信息：用户表有哪些字段？订单表有哪些字段？外键关系是什么？" |
| **甘特图缺少时间信息** | "画个项目甘特图" | "请提供：1. 项目有哪些任务/阶段？2. 各任务的起止时间或持续天数？3. 任务之间是否有依赖关系？" |
| **饼图缺少数据** | "画个部门预算饼图" | "请提供各部门的预算金额或占比数值。" |
| **类图缺少类信息** | "画个电商系统类图" | "需要包含哪些核心类？（如：User、Order、Product 等），以及它们之间的关系。" |

### 反问原则

1. **先澄清，再生成** — 不允许在信息不足时猜测生成
2. **给出选项** — 反问时提供可选方案，帮助用户决策
3. **一次问清楚** — 尽量把所有需要的信息一次性问完，避免反复追问
4. **复杂需求先拆分确认** — 元素超过 15 个时，先给出拆分方案让用户确认

## 核心语法规则（必须遵守）

这几条规则记死了，不然图画不出来：

### 1. 数字后面别加空格

```
❌ [1. 第一步]     → 会报错，被当成列表了
✅ [1.第一步]       → 去掉空格
✅ [① 第一步]       → 用带圈数字
✅ [(1) 第一步]     → 加括号
✅ [步骤1：第一步]  → 加前缀
```

带圈数字备选：① ② ③ ④ ⑤ ⑥ ⑦ ⑧ ⑨ ⑩ ⑪ ⑫ ⑬ ⑭ ⑮ ⑯ ⑰ ⑱ ⑲ ⑳

### 2. 子图名字有空格要加引号

```
❌ subgraph 核心模块
✅ subgraph core["核心模块"]
```

### 3. 引用节点用 ID，别用显示名

```
❌ 标题 --> 核心模块    → 不认识
✅ 标题 --> core        → 用 ID 才对
```

### 4. 特殊符号替换

```
英文引号 " → 用 『』
英文括号 () → 用 「」
换行 <br/> → 只在圆形节点 ((文字<br/>换行)) 中有效
```

### 5. 空格与双引号（⚠️ 最常遗漏）

**节点文本包含空格时，必须用双引号包裹**：

```
❌ API[API 网关]              ← 错误！空格导致渲染失败
✅ API["API 网关"]            ← 正确！双引号包裹

❌ DB[MySQL 主从]             ← 错误！
✅ DB["MySQL 主从"]           ← 正确！
```

**自检口诀**：只要节点文本有空格或中文标点，一律加双引号！

### 6. 箭头类型

| 写法 | 线型 | 用在哪 |
|-----|------|-------|
| `-->` | 实线箭头 | 正常流程 |
| `-.->` | 虚线箭头 | 可选、辅助、支持系统 |
| `==>` | 粗线箭头 | 强调、重要路径 |
| `~~~` | 不可见连线 | 仅用于布局占位 |

### 7. ER 图特殊规则

**表名格式：**
- 所有表名统一添加中文备注后缀，格式：`表名(中文备注)`
  ```
  ❌ JM_EMPLOYEE_INFO
  ❌ JM_EMPLOYEE_INFO["JM_EMPLOYEE_INFO(表)"]
  ✅ JM_EMPLOYEE_INFO["JM_EMPLOYEE_INFO(员工信息表)"]
  ```

**关系符号参考：**

| 符号组合 | 关系类型 | 说明 |
|---------|---------|------|
| `\|\|--\|\|` | 一对一 | 两边都是一 |
| `\|\|--o{\|` `\|\|--\|{` | 一对多 | 箭头指向多方 |
| `}o--\|\|` `}\|--\|\|` | 多对一 | 箭头指向一方 |
| `}o--o{\|` `}\|--\|{` | 多对多 | 两边都是多 |

**正确示例：**
```mermaid
erDiagram
    JM_EMPLOYEE_INFO["JM_EMPLOYEE_INFO(员工信息表)"] ||--o{ JIS_COMMUNITY_POST["JIS_COMMUNITY_POST(社区帖子表)"] : "创建"
    JM_EMPLOYEE_INFO["JM_EMPLOYEE_INFO(员工信息表)"] }|--|| ORG_DEPARTMENT["ORG_DEPARTMENT(部门表)"] : "所属"
    JIS_COMMUNITY_POST["JIS_COMMUNITY_POST(社区帖子表)"] }o--|| JIS_COMMUNITY_COLUMN["JIS_COMMUNITY_COLUMN(专栏表)"] : "属于"
```

**按图表类型查阅详细语法：**
- 流程图/对比图/思维导图 → [references/flowchart-details.md](references/flowchart-details.md)
- **架构图（分层架构） → [references/architecture-diagram.md](references/architecture-diagram.md)**  
  ⚠️ **重要：架构图是流程图的"反向规则"**
  - 流程图推荐 `A --> B`（节点连接）
  - **架构图强制 `FE --> GW`（子图ID连接），严禁使用内部节点ID**
- 时序图/状态图 → [references/sequence-state-details.md](references/sequence-state-details.md)
- 报错排查/平台差异 → [references/common-rules.md](references/common-rules.md)

## 配置选项

所有图表都支持以下参数，按需使用：

**布局：**
| 参数 | 值 | 说明 |
|-----|---|------|
| `direction` | `TB`（默认） | 从上到下 |
| | `LR` | 从左到右 |
| | `RL` | 从右到左 |
| | `BT` | 从下到上 |

**详细度：**
| 参数 | 值 | 说明 |
|-----|---|------|
| `detail` | `simple` | 只保留核心元素，最少标签 |
| | `standard`（默认） | 平衡详细度，关键描述都带上 |
| | `detailed` | 完整注释、说明和元数据 |
| | `presentation` | 演示优化，字大细节少 |

**风格：**
| 参数 | 值 | 说明 |
|-----|---|------|
| `style` | `minimal` | 单色，干净线条 |
| | `professional`（默认） | 语义配色，层级清晰 |
| | `colorful` | 鲜艳色彩，高对比度 |
| | `academic` | 正式风格，适合论文/文档 |

**附加选项：**
| 参数 | 值 | 说明 |
|-----|---|------|
| `show_legend` | `true` / `false` | 是否加颜色/符号图例 |
| `numbered` | `true` / `false` | 步骤是否加序号 |
| `title` | 字符串 | 图表标题 |

## 使用模式

根据用户请求类型，选择不同处理方式：

**模式一：基础请求**
```
用户："画一个软件开发流程图"
处理：分析内容 → 选择 graph TB → 标准详细度生成
```

**模式二：带配置请求**
```
用户："画一个横向的销售流程图，要详细"
处理：分析内容 → 选择 graph LR → detailed 级别生成
```

**模式三：对比请求**
```
用户："对比传统开发和敏捷开发"
处理：分析内容 → 选择对比布局 → 用对比色生成
```

**模式四：交互请求**
```
用户："画一个系统交互的时序图"
处理：分析内容 → 选择 sequenceDiagram → 标准详细度生成
```

## 工作流程

1. **先理解你要画什么**
   - 搞清楚主体是什么
   - 有几个关键元素
   - 它们之间啥关系

2. **复杂需求先拆解**（元素超过 15 个时）
   - 把大需求拆成 2-3 个子图
   - 每个子图聚焦一个维度（如：先画整体架构，再画核心流程）
   - 用一致的节点 ID 和命名，方便组合
   - 示例：用户说"画一个电商系统，包括用户端、管理端、支付流程、订单流程"
      - 拆成：架构图（整体模块） + 支付时序图 + 订单状态图
      - 告诉用户为什么拆，并问要先画哪个

3. **选个合适的图**
   - 有先后顺序 → 流程图
   - 有分层结构、组件关系 → 架构图
   - 有交互 → 时序图
   - 有状态变化 → 状态图
   - 有层级 → 思维导图
   - 有循环反馈 → 循环图
   - 有对比 → 对比图
   - 数据库表结构关系 → ER图
   - 项目时间安排、任务进度 → 甘特图（查阅 [references/gantt-chart.md](references/gantt-chart.md)）
   - 占比分析、构成展示 → 饼图（查阅 [references/pie-chart.md](references/pie-chart.md)）
   - 面向对象设计、类结构 → 类图（查阅 [references/class-diagram.md](references/class-diagram.md)）

4. **选配置**
   - 用户指定了就用用户的
   - 没指定用默认值
   - 以可读性优先

5. **生成前强制自检**（必须完成，不能跳过）
   - **语法基础检查**：
      - [ ] 没有 `数字. 空格` 模式（如 `[1. 第一步]` → `[① 第一步]`）
      - [ ] 子图名字有空格的都用了 `id["显示名"]` 格式
      - [ ] 引用都用 ID，没用显示名
      - [ ] 特殊字符已替换：`"` → `『』`，`()` → `「」`
   - **图表类型特定检查**：
      - **如果是架构图** → 必须先读取 [references/architecture-diagram.md](references/architecture-diagram.md)，执行架构图强制审查流程（连线数、节点数、子图ID连接等）
      - **如果是流程图/对比图** → 确认节点连接逻辑清晰，同类节点合并（避免过度细化），无循环依赖（除非有意为之）
      - **如果是时序图** → 确认 participant 声明完整，消息方向正确
      - **如果是状态图** → 确认状态转换完整，有始有终
      - **如果是思维导图** → 确认层级结构清晰，不超过 4 层
      - **如果是ER图** → 确认表名有中文备注后缀`表名(中文备注)`
      - **如果是甘特图** → 必须先读取 [references/gantt-chart.md](references/gantt-chart.md)，确认日期格式正确、任务依赖关系合理、section 分组清晰
      - **如果是饼图** → 必须先读取 [references/pie-chart.md](references/pie-chart.md)，确认数据项在 3-8 个之间、标签简洁、数值正确
      - **如果是类图** → 必须先读取 [references/class-diagram.md](references/class-diagram.md)，确认类关系正确（继承/实现/关联/聚合/组合/依赖）、成员可见性标注规范
   - **输出前最终确认**：
      - [ ] 节点 ID 唯一（无重复）
      - [ ] 箭头语法正确（`-->` `-.->` `==>`）
      - [ ] 样式声明格式正确（`style A fill:#xxx,stroke:#yyy`）
      - [ ] 颜色用得一致（同语义用同色）
      - [ ] 方向已指定（TB/LR/RL/BT）
      - [ ] 没有 Emoji（用颜色或文字代替）
      - [ ] 兼容 Obsidian / GitHub 渲染器
   - **自检口诀**：
      ```
      写代码前先检查：
      - 数字后面无空格
      - 子图名字有引号
      - 引用只认 ID 名
      - 方向颜色要一致
      - ID唯一无重复
      - 架构图必须读 architecture-diagram.md
      ```

6. **生成代码**
   - 按规则写语法
   - 配上合适的颜色

7. **生成后自检**（必须完成，不能跳过）
   - **语法复查**：
      - [ ] 实际代码中没有 `数字. 空格` 模式
      - [ ] 实际代码中子图命名正确（`id["显示名"]`）
      - [ ] 实际代码中引用都是 ID
      - [ ] 节点 ID 无重复（实际检查代码）
   - **渲染预判**：
      - [ ] 箭头语法实际正确（`-->` `-.->` `==>`）
      - [ ] 样式声明实际格式正确
      - [ ] 没有 Emoji
      - [ ] 兼容 Obsidian / GitHub 渲染器
   - **视觉效果预判**：
      - [ ] 颜色用得一致（同语义同色）
      - [ ] 方向已指定
      - [ ] 布局是否清晰可读？太挤/太宽就调整
   - **架构图额外复查**（如果适用）：
      - [ ] 层级连线全是子图ID，没有节点ID连线
      - [ ] 连线数 ≤ 8 条
      - [ ] 核心节点 3-5 个
   - **ER图额外复查**（如果适用）：
      - [ ] 所有表名有中文备注后缀：表名(中文备注)
   - **甘特图额外复查**（如果适用）：
      - [ ] 日期格式统一（YYYY-MM-DD）
      - [ ] 任务ID唯一且有意义
      - [ ] section 分组逻辑清晰
   - **饼图额外复查**（如果适用）：
      - [ ] 数据项在 3-8 个之间
      - [ ] 标签简洁（8字以内）
      - [ ] 数值非负
   - **类图额外复查**（如果适用）：
      - [ ] 类名大驼峰命名
      - [ ] 成员可见性符号正确（+ - # ~）
      - [ ] 关系符号正确（<|-- <|.. --> o-- *-- ..>）

8. **输出结果**
   - 用 ```mermaid 包起来
   - 简单说下图的逻辑
   - 提及渲染兼容性（Obsidian、GitHub 等）
   - 可以问要不要调整或变体
