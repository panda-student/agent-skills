# 面向 PR 编程

AI 编码时代，代码产出速度已超过人的理解速度。防止代码变成黑盒的稳定做法：把 **PR（变更单元）当作编码的第一公民**——它既是人的**思考边界**，也是 AI 的**交付接口**。写代码时始终用「我要产出一个什么样、人能读懂、验得了、可回溯的变更单元」来组织工作。

## 三个支点

- **意图先于实现**：先写清 What / Why / 验收方式，再让 AI 写代码；写作倒逼思考
- **切片小到可读**：变更小到「人一口气读完并解释」，机制与行为分离
- **理解责任在人**：AI 产出 diff，人必须能解释每一处；解释不了就继续拆 / 补测试 / 补说明，禁止「看不懂先合」

## 统一术语：PR 循环

所有交付渠道共用同一循环，只是「变更单元」的载体不同（开源 = PR；公司 = MR / 提交集 / 提测单）。

Define（立单）→ Slice（切片）→ Prove（自证）→ Own（认领）→ Trace（留痕）

## Define · 立单（人的思考边界）

在动代码前完成变更单元的意图定义：

- 写清 What（用户可见变化）与 Why（根因 / 目标）
- 写明验收方式：打算用哪些命令 / 用例 / 截图证明它成立
- 划清边界：一个变更单元只解决一个问题；范围外的想法另立项
- 产出：PR 草稿 / 决策包 / 提测单——先有草稿，再填实现

## Slice · 切片（可审的交付单元）

- 机制与行为分开提交：先交无行为变化的扩展点，再交启用功能的改动
- 每个提交独立可编译、可测试、可回滚
- diff 自解释：命名清晰、贴合局部写法、无无关格式化 / 重排 / 顺手重构
- 具体编码判断（开闭、命名、模块归属、回落、显式配置）见 [coding-principles.md](./coding-principles.md)

## Prove · 自证（可复现的证据）

- TDD 先行：缺陷 = 复现用例，功能 = 行为用例
- 分层验证由内到外：目标单测 → 受影响范围全量 → 类型 / 静态检查 → 集成 / GUI
- 验证证据：实际命令 + 结果；UI 变更 before/after 截图或录屏；未做的验证写明
- 定量验证优于「看起来正常」（记录尺寸 / 位置是否恒定，而非只截一张图）

## Own · 认领（理解的闸门）

- 提交前以 reviewer 视角完整读一遍自己的 diff，逐处能解释
- 审的是「意图是否达成 + 是否可解释」，不是让 AI 自评
- 解释不了的 hunk 是红灯：补注释 / 补变更说明 / 回头拆小，禁止直接合入
- 提交前自审清单见 [coding-principles.md](./coding-principles.md)

## Trace · 留痕（未来的考古层）

- 变更单元（PR / MR / 提交信息）是 codebase 的考古层：What / Why / How-verified 完整
- 合并前保留分支与工作树，合并后按渠道回收
- 清理临时文件 / 凭据副本 / IDE 状态，不留杂物
- 理解项目 = 理解变更史；每个变更都要为未来的自己可读

## AI 协作协议（以 diff 为接口）

- AI 产出 patch / diff / PR，而不是在人眼皮底下直接改文件、人只看结果
- 小步循环：生成 → 读 diff → 并入，而非一次性大生成再一次性验收
- 读不懂的 hunk 当红灯：要求 AI 解释或拆小，不允许「先合了再看」
- AI 自评不算评审；人的 diff 审阅是合并前的最终门禁

## 反模式（黑盒就是这样形成的）

- 写完一大坨再想怎么拆（倒置）
- 「AI 说没问题」就合，人不读 diff
- 机制 / 行为 / 配置 / 格式化混成一个提交
- 只有成功路径、没有验证证据
- 大变更 + 无 What/Why，三个月后自己都看不懂

## 一句话检查表

> 这个变更：一个意图？一口气读完？每处我能解释？验证能复现？三个月后还看得懂「为什么」？

## 与渠道 SOP 的边界

本文件只定义「如何以变更单元组织思考与交付」的通用方法。渠道相关操作由领域 SOP 负责：

- 渠道相关操作（上游 PR、公司禅道 / UAT、分支拓扑、发布同步等）由对应的领域 SOP 或项目规则负责；本技能不列举具体渠道技能名，避免反向依赖
- 交付机制由渠道决定，核心循环不关心「怎么落地」：开源用 PR，公司用 cherry-pick 到目标分支（基线随项目生命周期分流）
