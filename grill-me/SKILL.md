# Grill Me — 先澄清，后行动

当用户提出一个计划、想法、需求或任务，在动手实施前，用结构化的逐个追问与其对齐，直到双方形成共同理解。用户也可用 `/grill-me` 强制触发（例如 AI 没好好澄清就想动手时）。

## 硬约束（HARD GATE）

- **未与用户达成一致理解前，不写代码、不改文件、不执行任何实施动作。** 无论任务看起来多简单——"简单"任务正是未经检验的假设造成返工最多的地方。对齐理解后才开始实施。
- **凡有 2–4 个明确选项的决策，必须用 `AskUserQuestion` 工具提问，禁止用纯文字把选项列在聊天里让用户回复"选 1/选 2"。** 这是"每问必给推荐"的落地载体——工具会把选项和推荐项结构化呈现，省去用户手打、降低选择成本，也堵住"忘了给推荐"的退路。只有真正的开放问题（见 reference 第四章例外）才允许文本提问。

## 五条核心准则

1. **自查优先** — 能用工具/文件系统查到的事实（代码结构、配置、git 历史、现有约定等），直接去查，不要问用户。只有**决策**、以及**只有用户知道**的偏好/意图，才问。
2. **决策树驱动** — 先理清各决策点之间的依赖关系，按依赖顺序提问：后置决策必须等前置决策定了再问，不要把依赖后续回答的问题提前抛出。
3. **逐个追问，独立可合并** — 依赖链上的决策严格一问一答：拿到前置答案再问后续，绝不提前抛。但**互不依赖的独立决策**可合并进同一次 `AskUserQuestion`（最多 4 个），减少往返。判断标准：回答 X 是否需要先知道 Y 的答案？需要→别合并；不需要→可合并。无论合并与否，都不要一次抛出一堆让用户不知所措的文字。
4. **每问必给推荐** — 每个问题都附上你的推荐答案和理由，把用户的选择成本降到最低。选择类问题**必须**用 `AskUserQuestion`：推荐项放 `options` 首位、标签末尾标"（推荐）"，理由写进该选项的 `description`。只有真正的开放问题才用文本，且仍要给出推荐。
5. **决策权归用户** — 你负责给推荐和理由，但拍板的是用户。每个决策都等用户确认后再继续。

## 执行流程

1. **查** — 先把能自查的事实查清（读文件、grep、看 git log、确认现有约定），带着上下文再提问。
2. **树** — 列出待澄清的决策点及其依赖关系，排好提问顺序。
3. **问** — 按依赖顺序提问；选择类决策**用 `AskUserQuestion`**（推荐项置首位并标注），互不依赖的独立决策可合并进同一次调用（≤4）。每个问题都附推荐与理由。
4. **验** — 关键决策都对齐后，用一段话汇总你对整个计划的理解，请用户确认是否一致。
5. **动** — 用户确认理解一致后，才开始实施。

## 不适用场景

- 简单明确的任务（改错别字、读个文件、查一个事实）——直接做。
- 用户明确说"直接做""不用确认"时——尊重指令，跳过澄清。
- 纯查询/只读探查（不产生变更）——查完直接汇报。

## 与 brainstorming 的区分

- `brainstorming`：把模糊想法产出完整设计 spec 的创意流程（提 2-3 方案、写设计文档、转 writing-plans）。
- `grill-me`：针对用户已给出的计划，用逐个追问把细节和决策对齐的提问方法论，更轻、更通用，不强制产出 spec。
- 两者可叠加：brainstorming 的提问环节可按 grill-me 的方式来。
