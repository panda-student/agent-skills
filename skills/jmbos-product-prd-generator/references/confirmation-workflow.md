## 用户预览确认

根据问题数量和变更复杂度，智能选择确认策略，减少不必要的用户交互。

### 智能确认策略

| 确认级别 | 触发条件 | 确认内容 | 用户交互 |
|---------|---------|---------|---------|
| **自动确认** | 无任何验证问题 + 仅格式/措辞修正 + 变更范围 ≤ 1 个章节 | 不展示预览，直接输出 | 零交互 |
| **快速确认** | 仅有 Low 级别问题 + 变更范围 ≤ 3 个章节 + 无新增功能点 | 仅展示摘要 + 修复统计 | 用户确认一次即可 |
| **完整确认** | 有 Medium 及以上问题 + 变更范围 > 3 个章节 + 有新增功能点 + 有待确认项 | 展示完整预览 | 用户逐项确认 |

### 自动确认规则

满足以下**全部条件**时，跳过用户确认直接输出：

- 没有标注为"待确认"的项
- 没有需人工介入的问题
- 所有验证问题均为 Low 级别且已自动修复
- 变更范围仅涉及格式修正、措辞调整、字段补充等非结构性修改
- 用户输入中**没有**明确要求"确认后输出""检查后再输出"等

**自动确认时的输出**：
```
✅ 自动确认通过（0 个问题，无需人工介入）

变更摘要：修正了第 2.3 节的措辞，补充了 F-SYS-001 的字段英文名称
→ 开始输出最终文档...
```

### 快速确认内容

1. **变更摘要**：列出本次变更了哪些章节、哪些功能点
2. **修复统计**：列出自动修复项数量和详情
3. **待确认项**：如有，列出

**快速确认交互**：
```
📋 变更预览

变更范围：4.1 节 F-SYS-001 字段说明、4.2 节 F-SYS-002 业务规则
修复统计：自动修复 2 项（Low）

待确认：无

是否确认输出？[确认 / 查看详情 / 修改]
```

### 完整确认内容

1. **生成内容摘要**：列出文档结构、主要功能模块、关键指标
2. **待确认项**：列出所有标注为"待确认"或"未说明"的内容
3. **已执行修复**：列出自动修复的内容（供用户审核是否合适）
4. **需人工介入项**：列出需要用户决策的问题

### 确认结果处理

| 用户反馈 | 处理动作 |
|---------|---------|
| 确认通过 | 进入输出环节 |
| 修改意见 | 收集意见，更新生成，再次预览 |
| 补充信息 | 补充信息后重新生成，再次预览 |
| 查看详情（快速确认中） | 降级为完整确认，展示全部内容 |

**循环机制**：预览→用户反馈→修改→再次预览，直到用户确认通过或放弃。完整确认模式最多循环 3 次，3 次后标记为"需人工介入"并输出当前版本。

## 输出最终PRD

用户确认通过后，执行输出：

1. **写入文件**：按命名规范生成文件名并输出PRD文档
2. **生成索引文件**：在同一目录下生成索引文件，文件名固定为 `索引.md`
3. **显示摘要**：列出文档结构、功能模块数量、章节完整性
4. **报告修复**：列出已执行的自动修复（供追溯）
5. **标记待确认**：列出用户仍需补充/确认的内容

### 索引文件生成规则

PRD文档输出后，必须在其同目录下生成索引文件 `索引.md`，用于快速定位该目录下的所有需求文档。

**文件命名**：`索引.md`（固定名称，与PRD文档同目录）

**索引文件内容结构**：

```markdown
# 需求文档索引

> 本索引由 PRD 生成器自动生成，用于快速定位需求文档。

| 序号 | 文档名称 | 迭代版本 | 日期 | 文件路径 |
|------|----------|----------|------|----------|
```

**索引条目生成规则**：

- 每个PRD文档对应索引中的一行
- **序号**：按添加顺序递增
- **文档名称**：PRD文档的文件名（不含扩展名）
- **迭代版本**：取自PRD文档YAML头部的 `iteration` 字段
- **日期**：取自PRD文档YAML头部的 `date` 字段
- **文件路径**：PRD文档的相对路径（相对于索引文件所在目录）

**索引更新策略**：

| 场景 | 处理方式 |
|------|----------|
| 索引文件不存在 | 新建 `索引.md`，写入表头和当前PRD条目 |
| 索引文件已存在 | 读取现有索引，追加新PRD条目（如已有同文件名条目则更新而非重复添加） |
| PRD文档被删除 | 从索引中移除对应条目 |
| PRD文档被重命名 | 更新索引中对应条目的文档名称和文件路径 |

### 文档命名规范

生成的PRD文档必须遵循以下命名规则：

```
{系统名称}-{模块/功能描述}-需求说明书-{迭代版本}.md
```

| 组成部分 | 规范要求 | 示例 |
|----------|----------|------|
| 系统名称 | 产品正式名称，英文或中文均可 | OpenClaw、企业微信 |
| 模块/功能描述 | 中文业务名称，多模块用连字符连接 | 智能体工作台、订单管理-支付 |
| 文档类型 | 固定为"需求说明书" | 需求说明书 |
| 迭代版本 | 格式：vX.Y，与YAML头部iteration字段一致 | v1.0、v2.4 |

**命名示例**：

| 场景 | 文档命名 |
|------|----------|
| OpenClaw系统智能体工作台模块 v1.0 | `OpenClaw-智能体工作台-需求说明书-v1.0.md` |
| 企业微信注册登录模块 v2.3 | `企业微信-注册登录-需求说明书-v2.3.md` |
| 全量需求（覆盖所有模块） | `OpenClaw-全量需求-需求说明书-v2.0.md` |

**文件名要求**：
- 使用纯文本字符，避免特殊符号（仅允许连字符`-`）
- 系统名称中如包含空格，用连字符替代
- 模块/功能描述使用中文业务名称，与第 3.3 节功能模块划分表中的模块中文名称一致
- 迭代版本必须与文档 YAML 头部的 `iteration` 字段一致
- 文件扩展名为 `.md`
