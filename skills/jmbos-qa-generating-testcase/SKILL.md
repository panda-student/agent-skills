## 工作流

必须严格按照以下工作流顺序执行，禁止跳步、并步或绕过其中任一步骤。

**执行原则**：
1. **不清楚就问**：模块、菜单、需求范围不明确 → 暂停问用户
2. **用户确认后再继续**：用 AskUserQuestion 得到明确答复后才能往下走
3. **严格遵循模板格式**：生成前必须读取 `references/markdown-testcase-template.md`，输出格式必须与模板示例完全一致
4. **禁止行为**：
   - ❌ 关键信息不明确时继续生成用例
   - ❌ 自己猜模块/菜单名称
   - ❌ 用默认值替代用户确认
   - ❌ 输出格式与模板示例不一致

**通用取消处理**：在任何步骤中，用户表示"取消"、"退出"、"停止"等指令时，立即清理已生成的中间产物，输出"任务已取消，已清理临时文件"，然后结束任务。

### 阶段一：输入处理

#### 1. 用户触发与输入解析

**输入处理**：
- **索引定位**：提供迭代/需求名称时，通过 `project_workspace/01.项目迭代工作区/索引.md` → `4.测试/索引.md` 定位需求和历史用例；需知识图谱时通过 `project_workspace/02.项目知识图谱/索引.md` 定位
- **自动识别**：自动判断输入类型（迭代名称/需求名称/文件路径/需求文本）并处理

**错误处理**：
- 需求文件不存在 → 提示并询问（重新输入/粘贴需求内容/取消）
- 需求内容不足 → 提示并询问（补充需求内容/取消）

**模式判断**：

| 条件 | 模式 | 说明 |
|------|------|------|
| 无历史用例 | 标准模式 | 从TC-{模块名拼音首字母}-001开始全新生成，严格遵循模板格式 |
| 有历史用例 + 用户说"更新/修改用例" | 增量更新模式 | 保留编号，新增追加 |
| 有历史用例 + 无更新触发 | 询问用户 | 询问用户选择：全量重新生成 / 增量更新 |
| 涉及知识图谱变更（步骤2判断） | 综合模式 | 结合知识图谱分析 |

#### 2. 判断是否涉及知识图谱历史用例变更

**知识图谱历史用例变更**：需求涉及对已有功能的修改、调整、优化、重构（需读取知识图谱中的完整版历史用例进行对比分析）。

**判断逻辑**：
- 明确提到"修改/调整/优化"已有功能 → **涉及** → 进入步骤3
- 明确是"新功能/新增" → **不涉及** → 跳过步骤3
- **无法判断** → 询问用户："本次是否涉及已有功能的修改？"

#### 3. 读取知识图谱历史用例（仅步骤2判断为"涉及"时执行）

**定位方式**：通过索引定位，而非硬编码路径
1. 读取 `project_workspace/02.项目知识图谱/索引.md`
2. 找到测试用例分类下的相关模块
3. 定位到对应的**知识图谱级**历史用例文件
4. 读取内容进行对比分析

**目的**：识别**知识图谱级**历史用例的复用/变更/废弃情况，为用例设计提供参考。

**重要**：只读取分析，不修改知识图谱文件。

**错误处理**：
- **知识图谱用例不存在**：提示"未找到知识图谱历史用例文件"，询问用户选择（提供文件路径/跳过知识图谱分析/取消任务）
- **迭代用例与知识图谱不一致**：生成冲突分析报告（列出不一致的用例编号、内容差异），询问用户选择（以知识图谱为准/以迭代用例为准/手动确认每处冲突）

**输出**：（内部分析，不输出物理文件）对比分析结果用于后续用例设计参考

### 阶段二：核心流程

#### 4. 需求解析与分析

**核心任务**：提取测试要素 → 评估质量 → 识别问题 → 确认模块归属

**需求分析检查清单**：

| 检查维度 | 检查项 | 具体做法 | 有问题时暂停 |
|----------|--------|----------|-------------|
| **提取测试要素** | 功能点 | 核心功能、正常流程、分支流程 | 不知道测什么 |
| | 边界值 | 有约束字段→识别边界内/边界值/超界/空值 | 边界不清楚 |
| | 异常场景 | 错误输入、系统异常、网络异常 | 出错怎么办 |
| | 业务规则 | 前置条件、互斥规则、状态转换 | 规则有矛盾 |
| | 非功能需求 | 性能、安全、兼容性要求 | — |
| **评估需求质量** | 可测性 | 区分能测的/需澄清的 | — |
| | 冗余 | 找重复：等价类/场景/功能点 | — |
| | 冲突 | 找矛盾：逻辑/规则/流程 | 规则有矛盾 |
| | 等价类 | 有效类1~2个，无效类各1个 | — |
| | 覆盖要求 | 需求拆条目编号，每条至少1用例 | — |
| **确认模块归属** | 模块 | 1.找需求文档中明确定义的模块名称; 2.没找到→暂停问用户 | **模块不知道** |
| | 菜单 | 1.确认功能点所属的具体菜单; 2.对应不到→暂停问用户 | **菜单不知道** |

**模块与菜单识别规则**：菜单路径第一级=模块，末级=菜单

**确认顺序**：先确认模块 → 再确认菜单。模块不明确时先问模块，模块确定后再问菜单。

**暂停后流程**：
1. 写 `clarification-questions.md` 记录问题
2. 向用户提问（问题简洁、选项简短）
3. 更新需求理解

**检查要点**：边界清晰、规则无歧义、异常有覆盖、性能可量化、验收可判定、逻辑无矛盾

**生成**：`project_workspace/01.项目迭代工作区/{迭代}/4.测试/.temp/{需求名称}/requirements/`
- `clarification-questions.md`（如有疑点）
- `change-impact-analysis.md`（增量模式）

#### 5. 需求条目化与索引（必做）

**5.1 模块分组**
- 根据步骤4.4的模块归属，将需求条目按模块分组
- 生成模块列表：如 `["质量保障", "QA工作台"]`

**5.2 索引生成**
- 为每个模块生成独立的需求索引：`requirements-index-{模块名}.md`

输出：`project_workspace/01.项目迭代工作区/{迭代}/4.测试/.temp/{需求名称}/requirements/`
- `requirements-index-{模块名}.md`（各模块独立索引）

#### 6. 测试设计策略

严格应用 `references/testcase-design-strategy.md` 的覆盖策略进行用例设计。

#### 7. 生成可执行测试用例

**设计规范**：严格应用 `references/testcase-design-strategy.md` 的规范，确保：
- 用例编号、优先级、类型标记符合规范
- 每条用例标记覆盖的需求条目

**模式处理**：
- **标准模式**：全新生成，不涉及历史用例变更
- **增量更新模式**：新增条目设计全新用例，删除条目删除关联用例，修改条目更新受影响用例，未变更原样保留

#### 用例编号处理规则

| 模式 | 核心策略 | 编号规则 |
|------|----------|----------|
| **标准模式** | 全新生成 | TC-001 起连续编号，无断号 |
| **增量更新模式** | 保留历史编号 | 新增用例在末尾追加（TC-006），删除/修改/未变更保持原编号不变，允许断号 |
| **综合模式** | 全量重新编号 | 所有用例重新连续编号（TC-001~TC-XXX），废弃用例剔除 |

> 用例编号示例见附录B

**7.1 模块级用例生成**
- 遍历每个模块
- 为每个模块生成独立的用例树：`case-tree-{模块名}.md`
- 用例编号按模块独立编排（如 TC-质量保障-001、TC-QA工作台-001）

生成：`project_workspace/01.项目迭代工作区/{迭代}/4.测试/.temp/{需求名称}/case-tree/`
- `case-tree-{模块名}.md`（各模块独立用例树）

#### 8. 质量门禁与闭环

**前置条件**：步骤4-7的中间产物已物理生成

**覆盖矩阵校验**：
- 生成 `reports/coverage-matrix.md`（基于模板 `references/coverage-matrix-template.md`）
- 验证每个需求条目至少映射1条用例
- 未覆盖条目数必须 = 0

**质量校验**：字段完整性、规范符合性、用例独立性

**闭环规则**：
- 覆盖不全时，不结束任务；必须继续补写用例直到覆盖门禁通过
- 禁止在覆盖门禁失败状态下输出最终 Markdown

**执行顺序**：
1. 生成 requirements/ 目录文件
2. 生成 case-tree/case-tree-{模块名}.md（各模块独立文件）
3. 生成 reports/coverage-matrix.md
4. 执行校验 → 通过进入步骤9，不通过返回步骤7

**门禁检查清单**（必须全部通过）：

| 检查项 | 标准 |
|--------|------|
| 中间产物 | `requirements/`、`case-tree/`、`reports/` 已生成 |
| 用例文件内容 | 仅用例列表 + 假设与未决事项 |
| 用例文件不包含 | 统计表格、覆盖矩阵 |
| 覆盖率 | 100%（每个需求至少1条用例）|
| 质量 | 字段完整、规范符合、用例独立 |

未通过门禁 → 返回步骤7补写用例，直至通过。

### 阶段三：输出交付

#### 9. 输出 Markdown 格式测试用例

**读取模板**：`references/markdown-testcase-template.md`
**模板应用**：生成的用例必须严格按照模板定义的格式（层级结构、编号规则、字段格式）

**9.1 正式输出文件**

| 场景 | 文件命名 | 存放路径 |
|------|----------|----------|
| 单模块 | `{需求名称}_测试用例_{YYYY-MM-DD}.md` | `project_workspace/01.项目迭代工作区/{迭代}/4.测试/测试用例/` |
| 多模块（≥2个） | `{需求名称}_测试用例_{模块名}_{YYYY-MM-DD}.md` | `project_workspace/01.项目迭代工作区/{迭代}/4.测试/测试用例/` |
| 汇总文件（可选） | `{需求名称}_测试用例_汇总_{YYYY-MM-DD}.md` | `project_workspace/01.项目迭代工作区/{迭代}/4.测试/测试用例/` |

- 多模块场景下，每个模块生成独立的用例文件
- 汇总文件仅在多模块或用户明确要求时生成，包含所有模块的用例概览

**9.2 中间产物**

| 路径 | 说明 |
|------|------|
| `.temp/{需求}/requirements/` | 疑点清单、模块索引、变更分析 |
| `.temp/{需求}/case-tree/` | 各模块用例树 |
| `.temp/{需求}/reports/` | 覆盖矩阵、门禁结果 |

#### 10. 任务完成与清理

**任务完成标志**：
- 输出"测试用例生成完成！"
- 列出生成的所有文件路径
- 提示用户查看输出结果

**清理指令**：
- 保留正式输出文件（`测试用例/` 目录下的 `.md` 文件）
- **可选清理**：询问用户是否清理中间产物（`.temp/` 目录）
- 若用户选择清理，删除 `.temp/{需求名称}/` 目录
