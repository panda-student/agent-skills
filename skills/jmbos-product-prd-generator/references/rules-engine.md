# PRD 统一规则引擎

本文件是 PRD 生成器的唯一规则定义源。所有验证规则在此定义一次，生成阶段和验证阶段均引用此文件。

> **设计原则**：一次定义，多处引用；分层验证，增量修复。仅保留不可违反的硬约束，指导建议由模型按场景灵活处理。

---

## 规则分层体系

| 层级 | 名称 | 验证时机 | 验证范围 | 不可跳过 |
|------|------|---------|---------|---------|
| L1 | 快速规则 | 生成时每个章节写入后立即执行 | 当前章节 | 是 |
| L2 | 标准规则 | 生成后对变更部分执行 | 变更章节 + 关联章节 | 是 |
| L3 | 深度规则 | 用户确认前执行（可选） | 全文档 | 否 |

### R2.4 功能详情要素完整性

每个功能点包含 12 项要素（11 必需 + 1 可选，与 prd-template.md 对齐）。

| 规则ID | 规则描述 | 必需/可选要素 |
|--------|---------|---------|
| R2.4.1 | 功能点要素齐全 | 必需(11)：功能ID、关联用户故事、功能描述、前置条件、后置条件、主要流程、异常与分支流程、业务规则、页面交互说明、页面字段说明、EARS格式需求列表；可选(1)：子流程分组（仅当含多Tab/子操作时） |
| R2.4.2 | EARS列表覆盖主要流程操作意图 | 逐条比对主要流程的"用户操作意图"与EARS条目，每个操作意图至少对应1条EARS需求（一个意图可覆盖连续多个步骤），识别无对应EARS的意图并补充 |
| R2.4.3 | EARS列表覆盖异常与分支流程 | 逐条比对异常与分支流程条目与EARS条目，每个独立异常/分支条件（不同触发条件或不同提示文案）至少对应1条EARS需求 |
| R2.4.4 | EARS列表覆盖核心业务规则 | 逐条比对业务规则条目与EARS条目，仅核心业务约束（唯一性/跨字段/权限/状态流转）至少对应1条EARS需求；字段长度、枚举取值、格式正则等非核心约束不强制要求EARS |

**深度感知**：功能点要素要求根据 YAML `depth` 字段调整：

| 深度 | 必需要素 | 可选/省略要素 |
|------|---------|-------------|
| Lite | 功能ID、关联用户故事、功能描述、主要流程、EARS格式需求列表（5项） | 前置条件、后置条件、异常与分支流程、业务规则、子流程分组、页面交互说明、页面字段说明均省略 |
| Standard/Full | 11 项必需 + 1 项可选（子流程分组），详见 prd-template.md | 无 |

Lite 深度不适用 R2.4.1 的 11 项必需要求，仅校验 5 项核心要素。R2.4.2-R2.4.4 的 EARS 覆盖检查在 Lite 深度时仅校验主要流程的 EARS 覆盖（R2.4.2），异常流程和业务规则的 EARS 覆盖（R2.4.3-R2.4.4）不强制要求。

### R2.10 EARS 语法分级应用

需求描述和验收标准的 EARS 语法按功能优先级分级应用，平衡质量与效率：

**EARS 模式中英对照**（本技能统一使用中文名称）：

| 中文名称 | 英文名称 | 说明 |
|---------|---------|------|
| 通用需求 | Ubiquitous | 无前置条件，系统在任何情况下都应满足 |
| 事件驱动 | Event-Driven | 当特定事件发生时 |
| 状态驱动 | State-Driven | 当系统处于特定状态时 |
| 可选特性 | Optional Feature | 当某功能被启用时 |
| 条件异常 | Unwanted | 在特定条件下执行但存在例外情况 |

| 规则ID | 优先级 | EARS 要求 | 检查方法 | 修复动作 |
|--------|-------|----------|---------|---------|
| R2.10.1 | **P0** | 严格 EARS：每条需求必须使用标准 EARS 句式，包含主句 + 条件从句 + 异常从句 | 逐条检查需求的 EARS 句式完整性 | 补充缺失的从句，确保句式完整 |
| R2.10.2 | **P1** | 简化 EARS：保留通用需求和事件驱动两种句式，可省略次要从句 | 检查至少包含一种 EARS 句式 | 将自然语言描述改写为 EARS 句式 |
| R2.10.3 | **P2-P3** | 轻量 EARS 或自然语言 | 检查是否使用"系统应当"句式 | 将"可以""建议"类描述改为"应当"句式 |

**验收标准检查**：

| 规则ID | 优先级 | 要求 | 检查方法 |
|--------|-------|------|---------|
| R2.10.4 | **P0** | 验收标准必须使用 EARS 语法，3-5 条；必须包含关联功能点ID、预期结果 | 逐条检查 EARS 格式、关联列和预期结果列是否填写，计数 |
| R2.10.5 | **P0** | 验收标准不得与 4.x EARS 需求列表逐条复制 | 检查 7.1 验收条件是否与 4.x EARS 描述完全相同（允许提炼，不允许逐条复制） |
| R2.10.6 | **P0** | 指标验收标准必须关联第5章非功能需求章节 | 检查关联非功能章节列是否填写且指向 5.x |

## 验证策略

### 分层执行

L1/L2/L3 三层验证的执行时机与范围见本文档开头的「规则分层体系」表。L1 在生成时即时执行（不可跳过），L2 仅对变更范围+关联章节执行（不可跳过），L3 在用户确认前可选执行全文档验证。

### 增量验证规则

当执行增量验证时，**验证范围**限定为：

| 变更类型 | 验证范围 |
|---------|---------|
| 新增功能点 | 该功能点所在章节 + 功能清单表 + 功能点索引表 |
| 修改功能点 | 该功能点所在章节 + 受影响的关联章节（如跨模块引用） |
| 新增模块 | 该模块所有章节 + 功能清单表 + YAML `modules` 字段 |
| 修改产品概述 | 第 2 章 + 第 7 章验收标准（如目标变更） |
| 修改非功能需求 | 第 5 章 + 第 7 章指标验收 |
| 修改验收标准 | 第 7 章 + 关联功能点的第 4 章 |
| 仅格式修正 | 仅修正涉及的行，不触发全量验证 |

## 修复机制

### 修复优先级

| 级别 | 名称 | 判定条件 | 修复策略 |
|------|------|---------|---------|
| Critical | 必须修复 | 缺少必需章节、内容与用户输入根本不符 | 立即自动修复 |
| High | 必须修复 | 功能遗漏、关键指标不可量化 | 立即自动修复 |
| Medium | 建议修复 | 跨章节不一致、验收标准不完整 | 自动修复，标注变更 |
| Low | 可选修复 | 格式问题、术语不统一 | 自动修复 |

### 增量修复流程

```
1. 执行分层验证 → 输出"问题清单 + 影响范围"
2. 按优先级排序问题
3. 对每个问题：
   a. 执行修复动作
   b. 仅重新验证该问题的影响范围（不重跑全量）
   c. 判断：
      - 通过 → 继续下一个问题
      - 失败且可修复 → 返回步骤 a（单问题最多 5 次）
      - 失败且不可修复 → 标记"需人工介入"
4. 所有问题处理完毕后，输出修复报告
```

### 不可自动修复的问题

以下问题标记为"需人工介入"，不自动修复：

- 需要业务决策的优先级问题
- 需要技术验证的性能指标
- 需要用户确认的功能范围争议
- 需要第三方确认的依赖信息
