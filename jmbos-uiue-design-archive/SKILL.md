## 文档索引

| 文件                                         | 内容                                 | 何时打开           |
| ------------------------------------------ | ---------------------------------- | -------------- |
| **references/archive-spec.md**             | 归档整合规范（产物格式、合并规则、反向拉取规范、路径转换）      | 执行任何归档/拉取操作前必读 |
| **references/design-delivery-template.md** | 设计交付物标准模板（HTML/文档元信息格式）            | 生成归档文件时参考      |

> **版本管理策略**：归档时直接覆盖，不做版本递增。历史版本由 git 仓库管理，知识图谱始终保存最新全量状态。详见 [archive-spec.md](references/archive-spec.md) §一。

## 工作流

必须严格按照以下工作流顺序执行，禁止跳步或绕过。详细规则详见 [archive-spec.md](references/archive-spec.md)。

### 模式选择

| 模式        | 触发条件            | 说明                   |
| --------- | --------------- | -------------------- |
| **单迭代归档** | 用户指定单个迭代名称归档    | 归档指定迭代的 UI 设计产物到知识图谱 |
| **批量归档**  | 用户要求批量处理或指定多个迭代 | 逐个迭代执行归档流程           |
| **反向拉取**  | 新迭代需基于历史归档版本修改  | 从知识图谱拉取历史产物到新迭代目录    |
| **完整性检查** | 用户要求检查归档状态      | 仅执行检查，不执行归档操作        |

> 默认进入**单迭代归档**模式，除非用户明确指定其他模式。

***

## 归档工作流（单迭代归档 / 批量归档）

### 1. 确定迭代目录

* 从用户输入中提取迭代名称（如 `20260101-迭代需求名称`）。

* 若用户未指定迭代，必须中断并列出 `01.项目迭代工作区/` 下所有已有迭代目录供用户选择。

* 迭代目录完整路径格式：`01.项目迭代工作区/{YYYYMMDD-迭代名称}/`。

* 确认后读取该迭代目录下的 `2.UI/索引.md` 了解已有产物。

**前置校验**：

| 校验项      | 通过标准                            | 不通过时             |
| -------- | ------------------------------- | ---------------- |
| 迭代目录存在   | 目录路径有效                          | 中断并提示用户          |
| 2.UI目录存在 | `{迭代}/2.UI/` 存在                 | 提示"该迭代无UI设计产物"   |
| 产出物存在    | `{迭代}/2.UI/` 下有产出物（排除tmp，非索引文件） | 提示"该迭代无已交付的设计产物" |

> 若 `2.UI/` 下仅有 `tmp/` 和 `索引.md`（无产出物），提示用户先完成设计并通过自检后再归档。

***

### 2. 扫描源设计产物

扫描 `{迭代目录}/2.UI/` 下的所有设计产物（排除 `tmp/`）。

**产物类型识别**：详见 [archive-spec.md](references/archive-spec.md) §一。

**元信息提取**：详见 [archive-spec.md](references/archive-spec.md) §三。关键字段：产物编号、页面名称、所属模块（归档分目录依据）、需求来源。

**产物分组**：按"所属模块"字段分组，无法确定时归入"通用"目录。输出《源产物清单》。

***

### 3. 读取知识图谱已有产物

读取 `02.项目知识图谱/2.UI/` 下的已有内容。

**目标目录结构**：详见 [archive-spec.md](references/archive-spec.md) §4.1。知识图谱区 `pages/` 按模块分目录。

**已有产物比对**：按产物编号、页面名称、功能模块三个维度匹配。输出《已有产物比对表》。

***

### 4. 整合设计产物

> **核心策略**：直接覆盖，不做版本递增。详细合并规则详见 [archive-spec.md](references/archive-spec.md) §4.2。

**整合要点**：

| 产物                     | 整合方式                       | 规范引用                                                    |
| ---------------------- | -------------------------- | ------------------------------------------------------- |
| 页面 HTML + 配套 JS        | 按模块分目录，直接覆盖                | [archive-spec.md](references/archive-spec.md) §4.2      |
| index.html             | 直接覆盖到 `设计稿/` 根目录           | [archive-spec.md](references/archive-spec.md) §4.2 唯一入口 |
| common.css / common.js | 直接覆盖到 `设计稿/css/`、`设计稿/js/` | [archive-spec.md](references/archive-spec.md) §4.2 公共资源 |
| 设计文档                   | 直接覆盖                       | [archive-spec.md](references/archive-spec.md) §4.2      |
| 图片素材                   | 按模块归类，直接覆盖                 | [archive-spec.md](references/archive-spec.md) §4.2      |

**模块目录确定**：从文件元信息头"所属模块"字段读取，无法确定时归入"通用"目录。详见 [archive-spec.md](references/archive-spec.md) §4.2 模块目录确定逻辑。

**路径转换**：归档时 `common.js` 的 `pageRoute` 路径需从迭代区扁平格式转为知识图谱区模块格式。详见 [archive-spec.md](references/archive-spec.md) §4.3。

**过大模块提示**：若单个模块下页面（HTML + 配套 JS）超过 20 个，提示用户是否按子模块拆分目录。

***

### 5. 更新迭代区索引

更新 `{迭代目录}/2.UI/索引.md`：将已归档的产物条目标注"已归档"，记录归档日期和目标路径。格式详见 [archive-spec.md](references/archive-spec.md) §5.1。

***

## 反向拉取工作流（知识图谱 → 新迭代目录）

> **场景**：新迭代需要基于历史归档版本进行修改时，从知识图谱拉取相关产物到新迭代目录。详细规范详见 [archive-spec.md](references/archive-spec.md) §七。

### L1. 确定拉取范围

* 从用户输入中提取新迭代名称和本次迭代涉及的页面编号清单（如 D-001、D-005）。

* 若用户未指定页面编号，读取新迭代的需求文档，推断涉及的页面。

* 确认拉取清单后进入下一步。

**前置校验**：

| 校验项     | 通过标准                        | 不通过时             |
| ------- | --------------------------- | ---------------- |
| 知识图谱存在  | `02.项目知识图谱/2.UI/设计稿/` 存在    | 中断并提示"知识图谱无设计产物" |
| 页面文件存在  | 指定编号的 JS 文件在知识图谱中存在         | 提示"指定页面不存在于知识图谱" |
| 新迭代目录存在 | `01.项目迭代工作区/{新迭代}/2.UI/` 存在 | 提示用户先创建迭代目录      |

***

### L2. 执行拉取

按 [archive-spec.md](references/archive-spec.md) §7.2 执行拉取：

**拉取策略**（详见 [archive-spec.md](references/archive-spec.md) §7.1）：

| 资源类型                                             | 拉取策略     | 原因                    |
| ------------------------------------------------ | -------- | --------------------- |
| `index.html` / `css/common.css` / `js/common.js` | **全量复制** | 保留完整路由表，归档覆盖后知识图谱不丢路由 |
| `pages/D-XXX_{页面功能名称}.html` + `js/pages/D-XXX_{页面功能名称}.js`                                 | **按需拉取** | 只拉本次迭代涉及的页面 HTML + 配套 JS         |

> **关键**：`js/common.js` 必须全量复制。归档时直接覆盖知识图谱的 `common.js`，如果迭代区只配了局部路由表，归档覆盖后知识图谱会丢失未迭代页面的路由。

**执行步骤**：

1. 全量复制公共资源（index.html / common.css / common.js）
2. 按需复制页面 HTML + 配套 JS（HTML 去掉模块目录层级扁平化到迭代区 `pages/`，JS 扁平化到迭代区 `js/pages/`）
3. 路径转换：`common.js` 的 `pageRoute` 从模块格式转为扁平格式（详见 [archive-spec.md](references/archive-spec.md) §4.3）
4. 验证：迭代区 `index.html` 双击可打开，本次拉取的页面可正常预览

> **迭代期间预览说明**：`common.js` 路由表是全量的，但 `pages/` 目录只有本次拉取的文件。点击未拉取的页面时，`switchPage` 通过 `pageRoute` 路由未命中 / fetch HEAD 检测显示"该页面非本次迭代范围"提示，不会404白屏——迭代期间只需预览本次修改的页面。

## 完整性检查模式（独立流程）

当触发**完整性检查**模式时，仅执行以下步骤：

### C1. 扫描知识图谱现状

遍历 `02.项目知识图谱/2.UI/` 下所有文件，建立完整清单。

### C2. 对比所有迭代的设计交付目录

逐个检查 `01.项目迭代工作区/` 下各迭代的 `2.UI/` 目录（排除tmp）。

### C3. 输出差异报告

| 类别        | 内容                           |
| --------- | ---------------------------- |
| **未归档迭代** | 有设计交付但未在知识图谱中找到记录的迭代         |
| **孤儿文件**  | 知识图谱中有但无法追溯到任何迭代的文件          |
| **路径异常**  | common.js 路由表路径与实际文件路径不匹配的条目 |

## 约束

### 必须做

* 归档后迭代源文件**不删除**，仅在索引中标注"已归档"

* 每个归档/拉取操作必须输出报告

* 更新迭代区索引文件

* 归档时直接覆盖，确保知识图谱始终是最新全量状态

* 拉取时 `js/common.js` 必须全量复制

### 禁止做

* 禁止修改上游产物（PRD、接口文档、测试用例等）

* 禁止修改迭代区中的非UI文件

* 禁止将tmp内容归档（tmp不进 git 仓库，仅 `2.UI/` 下产出物可归档）

* 禁止在没有用户确认的情况下自动删除或移动知识图谱中的已有文件

* 禁止在迭代区 `pages/` 下创建模块子目录（迭代区保持扁平）

### 异常处理

| 异常场景         | 处理方式                 |
| ------------ | -------------------- |
| 迭代区无设计产物     | 中断并提示用户              |
| 目标路径冲突（编号冲突） | 暂停并请用户确认处理方式         |
| 迭代区索引文件缺失    | 按模板创建新索引文件           |
| 文件损坏/无法读取    | 记录到报告中并跳过该文件         |
| 拉取时知识图谱无对应页面 | 提示用户该页面不存在，确认是否为全新页面 |
