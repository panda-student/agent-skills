# 编码改动原则参考

本文件解释每条编码原则的判断依据、落地方法和反模式，是 Dev Flow Core「面向 PR 编程」循环 Slice（切片）/ Own（认领）阶段的具体编码判断。案例来自一次真实改动（OpenIDEA 的 “Files opened in associated applications”），用来说明原则如何落地，不是必须照搬的方案。

## 判断顺序

拿到一个改动需求时，按下面的顺序收敛，不要跳步:

项目约定 → 最小改动面 → 模块归属 → 命名 → 局部写法 → 配置方式 → 回落与测试 → 提交拆分

每一步都可能否定上一步的设计。越早发现“项目已有同类做法”,改动越小。

## 先读约定,再设计机制

**规则**:新增设置、默认值、注册表、扩展点之前,先在仓库里找同类功能,照它的机制实现。

**为什么**:项目约定是长期 review 的结果。为单个值引入新机制,会多出一层需要维护、需要解释、需要测试的东西。

**落地**:
- 读 `AGENTS.md`、`CONTRIBUTING.md`、目标模块的模块注释
- 找 2–3 个相邻功能的实现,比较它们的注册方式、默认值位置、错误处理
- 新方案至少能指出“与哪个现有功能同构”

**反模式**:
- 为了一个默认值新增独立的默认配置文件
- 为了一个设置新增首次启动 seed/迁移逻辑
- 为了一个功能新增目录或依赖

**实战案例**:默认值的三种尝试都被否——写死在查看器、独立的 defaults TOML 文件、首次启动写入 `settings.toml`。最终按项目约定放回 `Settings::default()`,和 `exclude`、`ignoredNames` 完全一致。用户的原话是“按项目统一的约定”。

## 开闭原则,能加不改

**规则**:优先通过新增注册表、可选钩子、前置检查来扩展;不改被多处依赖的公共类型、函数签名和现有测试。

**为什么**:公共类型的改动会扩散到所有调用方和测试,review 成本和回归风险远大于新增一个独立入口。

**落地**:
- 先问“能否新增一个旁路入口”,而不是改现有函数的返回值
- 新增的接口保持可选,旧实现不需要改
- 现有测试一行不改,新增独立测试文件

**反模式**:
- 为了表达一个新结果,把现有返回类型改成联合类型,连带改所有调用方和测试
- 在现有 provider 接口上增加必填字段

**实战案例**:最初方案是改 `resolveFileEditor` 的返回类型并新增 `{ kind: "external" }`。改为新增 `ExternalFileOpenHandler` 注册表 + `openFile` 里一行前置检查后,`resolveFileEditor`、`FileEditorResolution`、provider 接口和三个现有测试全部零改动。

## 保留既有命名

**规则**:已有名称能表达语义就不改名;新增类型只在现有名称无法表达时才引入。

**为什么**:改名会让 diff 变大、让 reviewer 重新建立心智模型,而且通常没有行为收益。

**落地**:
- 新概念先尝试用现有类型的组合表达
- 必须新增时,让新名字只描述新增的部分
- 不为了“更准确”重命名已有导出

**反模式**:
- 把 `FileEditorResolution` 改名成 `FileEditorAcquisition`
- 为了统一风格重命名无关函数

**实战案例**:用户明确指出 `resolveFileEditor` / `FileEditorResolution` 可读性足够,不应改名。最终连联合类型也不需要,原名称原样保留。

## 放进已负责该职责的模块

**规则**:几十行的新逻辑优先并入已经负责该职责的模块,而不是新建文件。

**为什么**:文件数增加会放大 review 成本;同一职责分散到多个文件后,下次修改容易漏。

**落地**:
- 读模块注释,确认现有模块的职责边界
- 新函数放在相邻同类函数旁边,保持文件内的组织顺序
- 测试并入现有的 describe/测试文件

**反模式**:
- 为一个纯函数新建 `xxx.ts`
- 为一个 OS 调用新建平台模块,而现有平台模块已经在做同类事情

**实战案例**:`associatedApplication` 并入 `fileKinds.ts`(它本来就回答“哪些文件用哪个 viewer”),`openWithSystemApp` 并入 `fileManager.ts`(它本来就在做 OS 集成和路径转换)。生产代码新增文件从 2 个降为 0。

## 贴合局部写法

**规则**:复制相邻函数的参数默认、helper 复用、错误处理、测试风格和导入顺序。

**为什么**:一致性能让 reviewer 把注意力放在逻辑上,而不是风格差异上;也能避免引入项目里没有的写法。

**落地**:
- 参数默认值照相邻函数写,例如 `os = usePlatform.getState().os`
- 能复用现有 helper 就不重写,例如 `fileManagerPath`
- 测试沿用现有 `it.each`、`afterEach`、局部常量和断言风格
- 不把新依赖引入原本自包含的模块

**反模式**:
- 在一个手写路径切片的模块里引入 `basename`
- 新测试自造一套 setup,而相邻测试已有可复用的模式

**实战案例**:OS 判断写成默认参数,与 `fileManagerName(os = ...)` 同构;路径转换复用 `fileManagerPath`;测试沿用相邻的 `it.each` 和 `afterEach`。

## 显式配置优先于启发式

**规则**:有副作用或不可逆的行为(执行程序、删除文件、发布)必须由显式配置驱动;不要用扩展名或内容猜测。

**为什么**:启发式在边界情况下会把“查看”变成“执行”。Windows 的 ShellExecute 对 `.exe` 就是执行,这类风险不能靠默认列表兜底。

**落地**:
- 把“哪些输入触发行为”做成可编辑、可审计的显式列表
- 默认列表只放低风险类型
- 权限边界(例如 Tauri scope)与业务列表分开说明

**反模式**:
- “未识别的二进制文件一律交给系统打开”
- 用文件内容猜测是否可执行

**实战案例**:否决“列表外一律外开”,改为显式关联列表 + `opener:allow-open-path` 的 path scope;默认只含 Office/PDF,不含可执行扩展名。

## 每个新分支都要有回落

**规则**:新增分支在失败、远程环境、权限拒绝时必须回落到旧行为;测试同时覆盖“没变的部分”。

**为什么**:新功能不能降低原有可用性。回落路径是最容易被遗漏、也最容易被 reviewer 追问的部分。

**落地**:
- 为每个新分支写出失败语义:返回 false、抛错、继续下一个 handler
- 失败只记录警告,不打断用户操作
- 测试覆盖:新行为、拒绝、失败、远程、显式绕过(如 `asText`)、已有状态(如已打开 tab)

**反模式**:
- 外开失败后弹错并终止打开
- 只测试成功路径

**实战案例**:外开失败或远程项目时返回 false,继续走原有图片/hex/文本逻辑;测试覆盖 SSH、dev-container、启动失败、`asText`、已打开 tab。

## 机制与行为分开提交

**规则**:先提交无行为变化的扩展点,再提交启用功能的改动;每个提交独立可编译、可测试。

**为什么**:reviewer 可以先把“机制对不对”和“产品语义对不对”分开审;出问题时也能用 `git bisect` 定位到具体一层。

**落地**:
- 第一个提交只做契约/注册表/前置检查,不注册任何实现
- 第二个提交注册实现、加配置、加权限
- 提交信息分别说明“无行为变化”和“用户可见变化”

**反模式**:
- 机制、行为、配置、格式化混在一个提交
- 第一个提交就带行为变化,导致无法独立验证

**实战案例**:`refactor(editor): add an extension point for externally opened files` 在前,`feat(viewers): open associated documents with the system application` 在后;前者不注册 handler,行为零变化。

## 提交前自审清单

- 新机制是否有项目先例;没有先例时能否改成现有机制
- 公共类型/函数签名/现有测试是否被改;能否改为纯新增
- 新文件能否并入已有职责模块
- 参数默认、helper、错误处理、测试写法是否与相邻代码一致
- 有副作用的行为是否由显式配置驱动
- 新分支失败时是否回落,测试是否覆盖旧行为
- diff 是否包含无关格式化、重排、顺手重构
- 每个提交是否独立可编译、可测试

## 与领域交付流程的边界

本文件只回答“代码应该怎么改”。以下内容由对应领域 SOP 负责,不要在这里重复:

- 渠道相关操作（上游基线 / PR / CI、公司禅道 / UAT / 分支拓扑 / 发布同步等）由对应的领域 SOP 或项目规则负责；本技能不列举具体渠道技能名，避免反向依赖
- 通用交付方法（PR 循环、TDD、分层验证、验证证据、AI 协作协议、反模式）→ [pr-oriented-programming.md](./pr-oriented-programming.md)

推荐顺序:先按本文件完成编码设计与自审 → 再按 [pr-oriented-programming.md](./pr-oriented-programming.md) 的 PR 循环与对应领域 SOP 走交付。
