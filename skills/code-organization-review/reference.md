# reference — 代码组织评审

## 评审基线分层（SSOT）

- 第一优先：`<workspace>/.trae/rules/code-organization.md` —— workspace 级通用规范，存在即作为强制基线（可能随项目演进而更新）
- 兜底：SKILL.md 内置评审清单 —— 仅当 workspace 无规范文件时使用，内容与规范默认版对齐
- 禁止把规范全文复制进其他技能或 SOP —— 各处只引用本技能，本技能只引用基线文件

## 评审范围判定

- 未提交变更：`git diff`（含暂存与未暂存）
- 指定文件：仅审指定文件的当前实现
- 分支差异：`git diff <base>`，行号取新侧（right side）
- 多行问题标 `[start, end]`；单行问题两者相同；单条评论行跨度 ≤ 100

## 组织维度判定细则

### 单文件单一职责

- 检查 diff 中新增/修改的文件是否混杂多种职责（如入口文件里出现协议实现、工具文件里出现业务规则）
- 大文件不是问题本身，职责混杂才是；典型信号：同一文件同时存在端点/地址常量、业务判定、IO 调用、输出格式化

### 纯决策与执行分离

- 业务硬规则（校验、阈值、状态机）应为无副作用函数：输入 → 判定 → 返回结果/错误信息
- 规则函数内出现网络/文件/数据库 IO 即违规

### 外部接口唯一出口

- 对外地址/端点应集中一处定义（附速查表）；业务代码中散落字符串拼接 URL、重复定义同一端点即违规

### 依赖单向

- 上层依赖下层；工具层/类型层禁止反向引用业务层；发现循环依赖即违规

### 命名自解释

- 函数名应无需读实现即可知功能；变量名不使用无上下文缩写；方法名不含「和/and」式多职责表述

### 同类能力统一

- 同类处理（格式化、转换、导出等）应收敛到统一实现；diff 新增实现与既有同类逻辑并存即标记

## 输出规范

| 列 | 内容 |
|---|---|
| No. | 序号 |
| 问题 | 组织维度 + 一句话结论 |
| 建议 | 改法（落到层/文件） |
| 代码位置 | [file:line](file:///绝对路径#L行号) 新版行号 |

- 无问题时输出「✅ 未发现代码组织问题」并简述检查范围
- 与通用评审技能发现重复时保留组织维度表述，避免重复条目

## 与通用代码评审的分工

| 维度 | 归属 |
|---|---|
| 正确性/性能/最佳实践/安全 | 通用代码评审技能（如 TRAE-code-review） |
| 分层/职责/接口出口/依赖/命名/统一性 | 本技能 |

- 两个维度可并行执行，结果合并呈现
