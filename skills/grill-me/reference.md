## 一、决策树提问法

grill-me 的骨架是"把待澄清的事项组织成一棵决策树，再按依赖顺序逐个问"。

### 1. 识别决策点

从用户的计划里提取所有"需要确定但尚未确定"的点。常见类型：

| 类型 | 例子 |
|------|------|
| 范围决策 | 做不做某子功能？覆盖哪些场景？ |
| 方案决策 | 用 A 方案还是 B 方案？ |
| 取舍决策 | 性能 vs 可读性？兼容旧版 vs 彻底重构？ |
| 约定决策 | 命名、目录位置、错误处理风格？ |
| 依赖/顺序决策 | 先做哪个？是否需要前置改动？ |

### 2. 判断依赖关系

对每对决策问自己：**回答决策 X，是否需要先知道决策 Y 的答案？**
- 是 → X 依赖 Y，必须先问 Y。
- 否 → 两者独立，可任意顺序。

**示例**：用户要"加一个导出功能"。
- "导出成 Excel 还是 CSV"（格式）→ 根节点，先问
- "Excel 用哪个库"（实现）→ 依赖格式，后问
- "文件名带不带时间戳"（约定）→ 独立，可穿插

### 3. 排序与提问

按依赖的拓扑序排列，从没有前置依赖的根节点问起。**每得到一个答案，重新检查剩余决策点**——用户的回答可能解锁、改变或取消某些后续决策。别机械地按初版列表问到底。

**独立决策可合并**：若几个决策互相没有依赖（回答任何一个都不需要先知道另一个的答案），可合并进同一次 `AskUserQuestion`（最多 4 个）以减少往返；有依赖的必须拆开，等前置答案回来再问。

## 二、自查优先判断清单

**先问自己：这个信息我能自己查到吗？** 能查到的，绝不问用户。

### 该自己查（别问）

- 代码结构、现有实现、函数签名 → Read / Grep
- 是否已有类似功能/工具/约定 → Grep / Glob
- git 历史、最近改动、谁改的 → git log / git blame
- 配置文件、依赖版本 → Read
- 报错信息、测试现状 → 跑命令 / 看日志
- 公开事实性知识（API 用法、框架行为）→ 查文档

### 该问用户（查不到的）

- 业务意图、目标、优先级
- 个人/团队偏好（"你更想要 A 还是 B"）
- 需要拍板的取舍决策
- 只有用户知道的上下文（线下约定、未来计划）

> **反模式**：grep 一下就知道有没有现成实现，却去问用户"我们有没有 XXX"。

## 三、正反例对照

### ❌ 反例：一次抛一堆

> "我需要确认几个问题：1）用哪个框架？2）要不要兼容旧版？3）错误怎么处理？4）文件放哪？5）要不要写测试？"

问题：信息过载，用户不知从何答起；且 3/4/5 依赖 1 的答案，提前问没意义。

### ✅ 正例：一次一个，带推荐，按依赖

> "先问最前置的：框架我推荐用 X（理由：项目已大量使用、团队熟悉）；选 Y 的主要风险是 ___。你倾向哪个？"
>
> （等回答）
>
> "好，用 X。下一个：兼容旧版我推荐保留（理由：___），但会增加 ___ 成本。你怎么取舍？"

### ❌ 反例：该自查的却问

> "我们项目里有没有现成的导出工具？"

### ✅ 正例：自查后再问决策

> （先 grep 确认）"我查到已有 `exportCsv` 工具。建议复用并扩展它，而不是新建。是否同意？"

### ❌ 反例：不给推荐

> "你想用 Excel 还是 CSV？"

### ✅ 正例：带推荐与理由

> "我推荐 CSV（理由：数据量小、无需样式、实现快）；除非你需要 Excel 的多 sheet/样式，那才值得上 Excel。你的场景是？"

### ❌ 反例：该用工具却用文字列选项

> "框架你想用 X 还是 Y？我推荐 X。"

问题：明明是 2 选 1 的决策，却写成文字让用户手打回复，没用 `AskUserQuestion`。用户选择成本高，推荐项也不醒目——这正是要消除的退路。

### ✅ 正例：走工具

> 用 `AskUserQuestion` 提问：`options` 首项"X（推荐）"，`description` 写"项目已大量使用、团队熟悉"；次项 Y 的 `description` 写主要风险。用户一键选定，无需手打。

## 四、提问方式：默认用工具，例外才用文本

**默认强制用 `AskUserQuestion`**：只要问题能拆成 2–4 个明确选项（范围/方案/取舍/约定等决策几乎都是），就**必须**走工具，不要用文字把选项列在聊天里让用户回复"选 1/选 2"。工具会把选项和推荐项结构化呈现，省去用户手打，也避免你"忘了给推荐"。

落地要点：
- 推荐项放 `options` 首位，标签末尾加"（推荐）"，理由写进该选项的 `description`。
- 互不依赖的独立决策可合并进同一次调用（最多 4 个）；有依赖的拆成多次，等前置答案回来再问后续。
- 工具自带的 "Other" 入口已覆盖自由作答，不必额外鼓励用户改用文字。

**仅这些情况允许文本提问（窄例外）**：
- 真正的开放问题——选项不可枚举，或你要听用户的方向性意见（"你对这个取舍怎么看"）。
- 选项本身需要大段背景铺垫、长解释才成立（即便如此，铺垫完仍尽量落到一次工具选择）。
- 纯流程确认（"理解一致，可以开工吗"）——这不是决策选择。

即便落在例外里用文本，仍要遵守：**附推荐 + 说理由 + 一次不超载**。

## 五、与 brainstorming 的边界

| 维度 | brainstorming | grill-me |
|------|---------------|----------|
| 定位 | 模糊想法 → 完整设计 spec | 已有计划 → 对齐细节与决策 |
| 产出 | 设计文档 + 转 writing-plans | 共识（不强制产出文档） |
| 提问 | 一次一个、提 2-3 方案 | 一次一个、每问带推荐、决策树驱动 |
| 重量 | 重（完整流程） | 轻（提问方法论） |

**叠加用法**：进入 brainstorming 后，其提问环节可按 grill-me 的"决策树 + 每问带推荐"方式执行，两者不冲突。

## 六、何时不启动 grill-me

- 任务简单且明确（改错别字、读文件、回答事实性问题）。
- 用户明确授权"直接做"。
- 纯查询/只读探查（不产生变更）。
- 用户在 grill 过程中明确说"够了，开始做"——立即转入实施，不要再问。
