# pms-dev-sop 阶段细则

> 基于「工程采购选项目字段缺失」等真实修复案例沉淀，统一覆盖缺陷修复与功能开发两类任务。与 [SKILL.md](./SKILL.md) 配套，SKILL.md 只做流程路由，本文承载全部执行细则。

## 阶段细则 {#阶段细则}

### 任务受理
- **判定任务类型**：缺陷修复（修不对的东西）还是功能开发（做没有的东西）；用户描述不明确时直接问用户，不脑补。类型决定前期确认的分诊走向
- 识别禅道单号（**不追问**）：用户发来禅道任务链接 → 有单号，从链接提取编号，全程携带（提交信息带编号、收尾填工时关单）；未发链接 → 非禅道任务、无单号，跳过所有禅道动作
- 记录任务输入物：
  - 缺陷修复：接口路径、UI 截图、接口文档截图、用户操作路径
  - 功能开发：需求描述/PRD、原型截图、接口文档、期望的用户操作路径

### 前期确认（按任务类型分诊，只读，不动代码）

#### 缺陷修复 → 受理验证
- Grep 定位 Controller → 顺调用链读 VO/SQL/Service
- 核对：接口出参是否包含契约字段（对照 docs/api 文档、前端 docs/business 业务文档）
- 输出「问题属实/误报」结论 + 数据源分析表（字段 → 来源表列 → 现状）

#### 缺陷修复 → 同类问题排查（问题确认属实后必做，误报跳过）
- 确认问题属实后，不要直接进入方案设计，先在项目内横向排查有没有同一类问题，避免修完一处再被逐个报出
- 排查维度（按本次缺陷特征选相关的几条，至少覆盖代码同源与数据同源两个方向）：
  - **同字段/同类字段**：同名字段、同业务含义别名在其他模块的取数，Grep 字段名/别名/SQL 片段
  - **同写法**：同一种实现范式在其他位置复用（同类 VO 映射、同类注解缺失、同类 SQL 出参别名、同类校验器照搬前端规则）
  - **同数据来源**：同一张表/同一个共有接口的多个消费方是否都受同一根因影响
  - **同前端形态**：同类页面组件/低代码菜单列绑定 prop 是否存在同样偏差
- 输出「同类问题清单」：位置（文件:行/菜单项）、场景、是否同源、影响面、建议是否本次一并处理；无同类问题也要明确写「已排查，无同类」
- 清单并入受理验证结论一起提交人工闸门，由用户拍板本次处理范围（全量处理 / 仅处理本次实例），**禁止只修单点就收尾**；用户选择「仅本次实例」时，在收尾说明中登记遗留的同类问题

#### 功能开发 → 需求梳理确认
- 通读需求输入物，Grep 定位涉及的模块/Controller/VO/SQL，摸清现状
- 梳理输出需求梳理表：
  - **业务目标**：一句话说清要做什么
  - **数据层**：涉及哪些表/字段；新增表/字段需明确 DDL 需求与存量数据影响（如存量行新列取值）
  - **接口层**：新增/修改哪些接口，出入参契约
  - **前端层**：涉及哪些页面/组件，是否需要前端同学配合
  - **范围边界**：明确本次做什么、不做什么
- 需求有歧义时用 AskUserQuestion 逐项澄清

#### 需求输入物作废识别（缺陷修复/功能开发通用）
- 规格书为 Excel 时逐格检查删除线：openpyxl 读取 `cell.font.strike is True` 即该行需求已作废；不能只看 `*` 必填标记与备注（字段作废后，依赖它的备注可能仍保留旧口径）
- 删除线作废的字段/规则不得作为校验或必填依据；已实现的必填/联动/条件显隐应回退，DDL 新增的同名字段与列一并下线
- 实例：2026-10-21 工程采购规格书 B6/C6「是否立项项目」带删除线（全簿仅此两格），后端按未划线的项目编号备注实现了条件必填，导致 UAT 提交被拦

#### 人工闸门（前期确认 → 方案设计）
- 前期确认产出（受理验证结论 + 同类问题清单 / 需求梳理表）输出后**必须停下汇报，等待用户人工确认**
- 用户确认后才发起方案设计；用户未确认前禁止自动进入方案设计，也禁止边等确认边预写方案

### 方案设计
- 前置：前期确认结论已经用户人工确认（见上方人工闸门）；未确认不发起
- 列出：改动点清单、数据来源映射（含跨模块字段名不一致的别名方案）、前端影响面
- 缺陷修复场景：改动点清单必须覆盖用户拍板的同类问题处理范围（全量则逐项列出，仅本次实例则说明剩余项）
- 缺陷修复场景附加目标：前端零改动；功能开发场景按需求梳理表给出分层改动方案
- **证据链闭环为标配**：无论用户是否质疑，方案中每个关键改动点与字段映射结论都必须附证据支撑：i18n 文案比对、业务文档归类、实体字段唯一性、DB 实际数据；用户质疑时逐项出示证据回应
- **多方案供选**：关键改动点至少给出 2 个候选方案（各自改动范围、影响面、成本/风险对比），标注推荐项与推荐理由，用 AskUserQuestion 由用户拍板，禁止单方案默认执行
- **共用接口场景化扩展**：被多方共用的查询/业务接口需为单一场景加差异行为（如过滤门槛、联动必填）时，在入参 DTO 加可选场景参数（默认 null/不传保持原行为）+ 实现处按参数分流，禁止复制出新接口——共用方零改动、行为可控；样板：`ProjectClosureSelectQueryDTO.ignoreInvestmentAmountThreshold`（项目结案 20 万门槛对工程采购申请场景放开，2026-10-21）
- 用户提出「为什么不统一命名」时：给改名连锁成本清单（DDL + 数据迁移 + 前端引用 + 文档）vs 最小改动对比，推荐最小方案；统一治理列为独立重构任务不混入本次任务
- 方案必须经用户确认后才进入实施（调用 `grill-me` 技能对齐）

### 实施（worktree 内，TDD 驱动） {#worktree-实施}
- **建树前先预检**（创建 worktree 之前先检查，不满足先处理再建树）：
  - **依赖**：比对将检出分支与主分支的 package.json + lock 文件是否一致 → 一致走 junction 复用，不一致计划树内独立 `npm ci`
  - **证书**：`.trae/certs/localhost-dev.pfx` 文件存在、检出分支 vite 配置已含 pfx 引用（若无则建树后需本地补配置）；首次用机先装系统受信
- **预检通过后创建 worktree 再动代码**：调用 `worktree` 技能建树，全部改动在树内进行
- **树内缺依赖时禁止全量重装**，按类型复用主仓库依赖（体积零增长 + 强一致）：
  - 后端 Maven：本地仓库 `~/.m2` 全局共享，树内天然复用主仓库依赖，直接编译即可，无需任何操作
  - 前端 node_modules：建 Windows 目录联接（junction）指向主仓库——`New-Item -ItemType Junction -Path "<树内>\pms_frontend\node_modules" -Target "<主仓库>\pms_frontend\node_modules"`；junction 不占磁盘体积，与主仓库依赖物理同源、完全一致
  - **junction 前提**：worktree 分支与主分支 lock 文件一致；本次任务新增/升级依赖时不可用，改为树内独立 `npm ci`，合并回主仓库后主仓库补 `npm install` 保持一致
- **按 TDD「红灯 → 绿灯 → 重构」循环开发** → 见下方 [TDD 实施规范](#tdd-实施规范)
- 只改指令指定位置，最小 diff；禁止顺手重构（TDD 重构仅限本次改动直接涉及的代码）
- 跨模块字段名不一致：在 SQL 出参加别名（`SELECT info.construction_project_no AS construction_account`），不改存量表结构和前端
- 涉及表结构变更（功能开发常见）：DDL 先经用户确认后再执行（dbx-database 技能，dbx MCP，凭据由 DBX 统一管理），并明确存量数据填充策略（默认值/回填脚本/留空待数据）

### 代码评审（编译与冒烟的前置闸门）
- 顺序固定：实施完成 → 先代码评审 → 评审问题改完 → 再编译验证 → 再本地简化冒烟（评审改动会推翻编译/冒烟结果，避免白跑）→ 合并推送后走 UAT 部署后终验
- 调用 TRAE-code-review，评审对象是**未提交的工作区变更**
- **代码组织维度**：并行调用 `code-organization-review` 技能专项评审（分层单一职责、纯决策与执行分离、接口唯一出口、依赖单向、命名自解释、同类统一）；基线为 workspace `.trae/rules/code-organization.md`，评审细则与输出格式以该技能为准，本 SOP 不复制
- **评审发现的问题不询问用户，直接全部修复**（含回归重审后新发现的问题，循环至通过），修复后自行回归，不停下等确认
- 评审重点核查项：DB 列存在性与驼峰映射、单测兼容性（断言方式是否被新增列破坏）、多消费方增量兼容、Service 后处理链路、字典/人员转换注解需求
- 发现问题 → 按影响面回归：仅涉本次改动 → 改完后重跑编译 + 本次冒烟；触及公共层 → 补跑相关单测；回归后重改再评审，循环至通过

### 编译验证
- `mvn -pl <目标模块> -am clean compile -q`；`clean` 必带（target/ 被 IDE 写坏增量状态会产生假通过）
- PowerShell 下 `-D` 参数必须加引号
- 触及公共层（SQL Provider、公共 VO）时补跑相关单测：`mvn -pl <模块> -am clean test "-Dtest=测试类名" "-Dsurefire.failIfNoSpecifiedTests=false" -q`
- 通过后仅反馈「编译通过」，不输出构建日志

### 本地简化冒烟（编译通过后，非通过依据）
- 仅接口层轻量冒烟：yaak 对本次改动核心接口打 1-2 发，确认无 500/契约级明显错误；改了后端可本地起服务直调，未改后端直调 UAT 现网接口
- UI 层 E2E 不在本地验证；前端/UI 改动的本地保障 = 树内写 vitest 单测并跑通（覆盖本次改动组件的渲染与交互逻辑，TDD 红灯-绿灯同规则），vitest 配置与踩坑以 `vitest` 技能为准
- 冒烟不要求证据链，发现问题就地修复后重新编译
- 冒烟目的仅是少把低级问题带上 UAT，**不作为「验证通过」依据**

### 合并提交推送
- 树内验证评审通过 → 用 `worktree` 技能合并回主分支
- **合并前先 fetch 核对远端领先**（实测 2026-10-22）：worktree 从旧基点切出，期间他人可能已推 origin/uat（含 dev 回流合并）——先 `git fetch origin uat`，`origin/uat..HEAD` 有领先提交属正常，但需检查 HEAD 是否已是 origin/uat 祖先；主仓库 uat 先 `merge --ff-only origin/uat` 再合并树分支。树分支改动文件若在远端新提交中也被演进（如页面 slots 大改），冲突解决以 uat 新版为基底、叠加本次改动（不回退他人功能）
- 提交信息：中文，「模块：一句话说明」；**有禅道单号则在信息中携带编号**（编号规则 → 见[禅道条件闭环](#禅道条件闭环)）
- 代码变更与构建产物分别提交、前端 dist 独立提交、uat→dev 全量同步、多仓库场景 → 统一规则见下方 [提交与分支同步](#提交与分支同步)
- **推送完成后必须删除本次任务的 worktree**：前置条件为该树已合并成功且已推送；调用 `worktree` 技能回收（含残留分支与目录清理），禁止遗留
- **字段物理下线（DDL 删列）时序**：代码合并推送后，先确认目标环境新镜像 Pod 启动时间晚于本次推送时间（Rancher 查看，见 `rancher-ops`），再执行 `DROP COLUMN`；否则旧 Pod 仍映射该列，查询/保存会报 `Unknown column`。执行序：`SELECT` 确认列存在 → `ALTER TABLE ... DROP COLUMN` → `information_schema.COLUMNS` 复查结果为 0 行

### 收尾说明
- 数据现状类遗留必须说明（如某字段 UAT 全空需有值数据后才能完整验证）
- 验证表述不超出实际覆盖终点：接口返回正确 ≠ 页面回显正确；宣称「验证通过/全链路打通」必须覆盖用户操作的完整链路终点，且每个通过项同步出示证据（要求见 [验证证据要求](#e2e-分层验证)）
- **临时文件及时清理**：临时产物在用途达成后立即删除，不积压到收尾才清——E2E 下载的导出验证文件与解压目录（内容核对完即删）、临时 SQL/调试脚本/日志文件（用完即删）；收尾时统一复查工作区与下载目录确认无遗留（树内残留随 worktree 回收一并清理）

### 经验复盘
- **前置**：合并提交推送（含 uat→dev 同步、worktree 回收）、UAT 部署后 E2E 终验通过、禅道条件闭环（有单号时）与收尾说明全部完成后执行；无论有无禅道单号均执行
- 调用 `learn` 技能对本次任务全流程复盘：踩坑与根因、流程断点、可沉淀的经验教训
- 复盘结论按 `learn` 技能规则固化到对应全局技能（如本 SOP 的踩坑预案）或项目规约文档
- 复盘只做沉淀，不回改已推送代码；无新经验时简要说明即可结束

## TDD 实施规范 {#tdd-实施规范}

> 实施阶段强制执行；完整规则以 `test-driven-development` 技能为准，本节为 SOP 内嵌约束。

### 红灯 → 绿灯 → 重构循环

- **红灯（先写失败测试）**：动手实现前，先写一个针对本次改动的测试并运行确认失败，禁止先写实现后补测试
  - 缺陷修复：测试即缺陷复现用例，先复现问题再修复，防止「修了但没修对」
  - 功能开发：测试描述新行为的预期契约（出入参、边界条件）
- **绿灯（最小实现）**：写恰好让测试通过的最小实现，不预设未来需求、不做多余设计；测试通过即进入下一阶段
- **重构（测试保护下优化）**：测试全绿后重构，聚焦四个目标——性能、代码质量、工程质量、可维护性；每完成一小步重构立即重跑测试保持绿灯，再进行下一步

### 适用性分诊

- **默认强制 TDD**：Service/Controller/VO/逻辑类 Java 改动（缺陷修复与功能开发均适用）；前端 .vue 组件/逻辑改动同规则写 vitest 单测（细则来源 `vitest` 技能）
- **可豁免（须向用户说明并经确认）**：纯 SQL 出参别名、DDL/数据迁移脚本、纯配置/文档类改动——不强行造测试，以 UAT 部署后 E2E 终验兜底
- 豁免判断不确定时问用户，不自行脑补

### 边界约束

- 重构范围仅限本次改动直接涉及的代码，禁止借 TDD 扩大 diff（与「最小 diff、禁止顺手重构」一致）
- 重构不是可选项：绿灯后存在明显性能问题、重复逻辑、命名不清、职责混杂时必须重构，再进入代码评审
- 循环迭代直至行为覆盖完整，再进入代码评审（评审问题改完后再编译验证）；触及公共层时按编译验证要求补跑相关单测

## E2E 部署后终验 {#e2e-分层验证}

> 2026-10-28 用户拍板：E2E 整体后置到 UAT 部署生效后执行，**终验通过才算验证通过**，本地只保留简化冒烟；本节全部规则（分诊、证据、UI 硬规则、异常裁决）验证对象一律为 UAT 真实环境。

### 终验前置：确认部署已生效（否则验证是假通过）

- push 后先跟踪 CI 流水线至镜像构建推送完成（`gitlab-operate` 技能），再经 Rancher 核对 UAT 目标服务 Pod 启动时间**晚于本次推送时间**（`rancher-ops` 技能）；Pod 未重启/镜像未更新前禁止开始终验
- 前端以 UAT 环境实际发布页面为准，不在本地起 vite 验证

### 分诊标准

| 层级 | 适用场景 | 手段 |
|---|---|---|
| **接口层** | 纯后端数据返回：缺陷类的字段缺失、取数口径、计算逻辑、筛选条件；功能开发类的新接口联调、新增字段核对 | use-yaak 技能直调 **UAT 环境**接口核对字段名与值（认证凭据从本地密码管理器 MCP 检索，不硬编码） |
| **UI 层** | 涉及前端交互链路：表单回显、列表展示、弹窗联动、导出下载、流程按钮、字典翻译、新功能页面操作 | 主：TRAE-browseruse-external 技能操作用户本机 Chrome（有登录态）访问 **UAT 环境**页面，纯 UI 操作走全链路；**浏览器搞不定时降级电脑控制**（trae-remote-official:computer-use 插件，Windows UI Automation） |

### 验证证据要求（结论为「通过」必附，两层通用）

- **禁止只报结论不出证据**：验证结论为「通过/PASS」时，必须随结论同步出示实际取证结果；不出示证据的验证点一律按「未验证」表述，不得计入通过项
- **证据分层**：
  - **接口层**：yaak 实际请求的 URL + 响应码 + 关键字段值摘录，逐项列出「期望值 vs 实际值」对照（对照本次修复点/新增契约字段，不贴无关大段报文）
  - **UI 层**：external_browser_network_requests 的请求/响应关键记录（响应码 + 关键出参）、DOM 断言结果（如 vxe-table `getCheckboxRecords()` 只读核实输出）、下载产物核对结论（文件实际生成 + 内容核对结果）；涉及视觉呈现/修复前后对比的附截图
- **证据与验证点一一对应**：每个验证点（字段回显/交互行为/页面形态）单独出示证据，禁止用一条笼统证据（如「页面正常」）覆盖多个验证点
- **证据不超覆盖终点**：接口层证据只证明接口返回正确，不得表述为「页面验证通过」；UI 层证据未覆盖的页面形态（如只验了详情页未验汇总页）单独列为未验证项

### UI 层验证硬规则
- **先连接再操作**：会话内首次使用外部浏览器前，先调 `browser_connect_plugin` 检查 Chrome 扩展连通性（该工具必须单独一轮调用，不可与其它工具合并）；未连接再调 `browser_setup_plugin` 引导用户完成配置
- **工具命名约定**：操作用户 Chrome 一律用 `external_browser_*` 前缀工具族（经 Exec 中 `await tools.external_browser_*` 调用），禁用无前缀 `browser_*`（会路由到内置浏览器丢失登录态）
- **纯 UI 交互模拟人工**：点击/输入/勾选走真实组件操作，禁止脚本直接赋值字段（避免绕过真实 UI 校验与形态问题）
- **裁决以网络层 + 产物为准**：external_browser_network_requests 核对请求体与响应码；下载类以下载目录实际文件为准——成功 toast 可能因内部 TypeError 静默失败，toast 不出现不代表失败
- **表格勾选状态用组件 API 核实**：vxe-table 用 `getCheckboxRecords()` 只读确认，不凭截图视觉判断
- **下载产物内容核对**：xlsx 改 `.zip` 解压直读 sheet1.xml（EasyExcel 内联字符串不走 sharedStrings）
- **浏览器搞不定就降级电脑控制**：外部浏览器路径反复失败（扩展连接不通且 setup 无法解决、验证码/系统弹窗挡道、canvas 等控件 external_browser_* 无法定位）或需跨应用操作（导出文件用 Excel 打开验证、Windows 对话框）时，改用电脑控制（trae-remote-official:computer-use）以 Windows UI Automation 驱动；两者都失败再按「连续 2 轮失败」规则停止汇报
- **验证终点覆盖产品实际查看的页面形态**：列表/汇总页与详情页互为独立验证终点，只验详情页回显不算覆盖链路终点（实例：2026-10-20 会签人员缺陷详情页正常、汇总页列恒空，被判「验证通过后复发」）
- **wujie 微前端面板内部元素原生点击受限时，用 JS 派发鼠标事件序列**：browser_click 报 `Hit test failed: would hit ... instead of ...` 且 scrollIntoView/坐标偏移重试均无效时，改用 evaluate 派发完整 mousedown→mouseup→click 事件序列模拟真实点击（仍属纯 UI 交互模拟范畴，非脚本赋值字段）（实例：2026-10-23 台账页漏斗筛选下拉，原生点击多次失败，JS 派发事件序列成功打开下拉并选中选项触发过滤请求）
- **列表排序类 UI 断言三要点**（实例：2026-10-23 效益 6 页签排序验证）：
  - vxe-table 固定列使 `.vxe-table--body-wrapper` 出现多份（每份都是全列副本，同一批数据被重复提取 3 次，分组断言全部失真）——取最后一个 wrapper 或按列数判别主表
  - 含中文的正则在 evaluate script 传输中可能静默失配（tds 明明含「第1年」，`/第(\d+)年/.test(joined)` 返回 false）——改用固定列索引 + `replace(/[^0-9]/g,'')` 提数绕开中文匹配
  - 断言模板 = 项目分组连续（同 code 只出现一段）+ 组内升序（日期/年度逐行不降），二者同时成立才算 PASS
- **SPA 已加载状态下同 tab 导航到其它路由可能不生效**（browser_navigate 返回后 `location.pathname` 仍是旧路由、console 无报错）——改用 `newTab: true` 打开直达成功；登录页表单同理：页面刷新后旧 ref 失效，先重新 snapshot 再填
- **弹窗"关不掉"/元素 hit test 被遮挡，先激活目标 tab 再定性**：后台标签页会暂停 CSS 动画，el-dialog 关闭 transition 的 animationend 不触发 → wrapper 残留可见并遮挡点击（Vue 状态 tagDialogVisible 已为 false、数据已刷新，仅 DOM 残留）；`browser_tabs activate` 后动画立即完成、wrapper 移除。弹窗类交互验证与异常裁决前必须先激活 tab，禁止把该环境现象当应用缺陷上报（实例：2026-10-26 流程测试用例标签编辑弹窗"保存后不关闭"，激活 tab 即消失）
- **E2E UI 验证排障的前置动作 = 记忆快查**：动手排障前先 Grep 项目记忆（project_memory.md）与 start-pms-backend 类技能文档中的环境配置经验，确认无现成方案再自行排查（实例：2026-10-28 低代码列表页同源化代理方案（url/commonUrl 双 cookie 翻转 + SPA 导航）记忆中早有完整记载且验证通过，未先查记忆导致重复排障 4 轮，最终用户拍板放弃本地 UI 验证改走 UAT 终验）
- **激活 tab 后弹窗内点击仍 hit test 失败的终极降级：evaluate 驱动 Vue2 实例调真实组件方法**：`document.querySelector('#app').__vue__` 起步，用 `$children` 递归定位含目标方法的组件（如弹窗外壳的 `selectProject`），直接调用真实方法（走真实代码路径：setProjectData 回填 + handleClose 关弹窗 + 级联加载全触发），再断言 DOM input 的 value 与 disabled——等价真实交互，不违反「禁止脚本直接赋值字段」（赋值是脚本写 formData；本方法是调用组件既有方法）。行数据用组件已有 `projectList` 或先 fetch 列表接口获取（实例：2026-10-27 变更表单选项目弹窗，行点击与"选择"按钮物理点击均失败，调 `shell.selectProject(row)` 后 formData 与「需求体系」DOM value 双断言通过）

### 异常裁决
- **浏览器取证结果互相矛盾时，第一时间开全新 tab 复验**：长期复用的自动化 tab 经反复导航/cookie 注入后 wujie 沙箱进入脏态，取证结果不可信；不在脏环境里继续加码排查，新 tab 复验正常即定性为环境假象、非应用缺陷（实例：2026-10-23 台账页漏斗排查，5 轮取证结果互相矛盾，脏 tab 中字典请求 pending、下拉 0 项、loading 卡死，全新 tab 复验字典请求 200×2、下拉 4 项正常渲染，判定无产品缺陷）
- **浏览器环境异常三信号**：手动 fetch 永久 pending + evaluate 报 Bridge error/Detached + 原生点击 hit test 失败，三者齐现即 wujie 沙箱脏态信号，先换全新 tab 复验再定性，禁止当应用缺陷上报
- 接口返回 null/空时先查库分界：库有值接口空 → 映射缺陷（代码问题）；库无值 → 数据现状（非代码问题），用 dbx-database（dbx MCP）统计填充率 + 取样例
- 空结果/400 先核对必填参数再怀疑改动：抽查前读目标 Controller/Service 方法签名与 DTO 确认必填入参（实例：`/benefit/report/ledger` 不传 `applyType` 时 Service 直接返回空页、`queryBudgetExpenseDetail` 不传 `projectCode` 报「项目编号不能为空」——均为缺参非改动问题，2026-10-23 实测）
- **连续 2 轮验证失败即停止**，汇报根因分析 + 方案选项（含回滚选项）由用户拍板，禁止暴力重试
- **终验不通过的处置**：立即停止验证并汇报（已通过项证据 + 失败点根因分析 + 方案选项含回滚），由用户拍板；返工按缺陷修复重新走流程（新 worktree → 评审 → 编译 → 合并 → 重新等部署生效 → 重新终验），禁止在已合并回收的旧树上继续提交

### 数据补偿：END_EVENT 回调重放 {#end-event-重放}

> 适用：流程结束回写链路缺陷修复后对存量单据做补偿回写，或回写失败排查后手动补触发（2026-10-28 预算变更 0303 单实证闭环）。

- 原始报文追溯：`t_ibpm_callback_log`
- 认证：外部直调需 Bearer（nisbos 登录链自动换 token）；yaak「PMS 后端」工作区 03-流程测试 分组已有现成请求「重放变更END_EVENT回调」，改 businesskey 即发

### worktree 前端本地启动证书方案 {#worktree-前端证书}

> 2026-10-28 起本方案仅用于实施期本地联调排查（可选）；E2E 已后置为 UAT 部署后终验，终验不依赖本地前端/后端环境。

- **根因**：新建 worktree 后 vite 若配置 `https: true`，每次启动自动生成一次性自签证书，未装入系统受信根证书颁发机构 → 浏览器报证书错误无法访问
- **方案**：改用固定自签证书（已装入系统受信的根证书颁发机构），统一归档于工作区 `.trae/certs/`，与主仓库共享同一物理路径，所有 worktree 直接引用绝对路径，无需重新生成/信任：

```js
// 固定自签证书（已装入系统受信的根证书颁发机构；统一归档于工作区 .trae/certs，与主仓库共享）
// 口令不硬编码：配置时从本地密码管理器 MCP 检索（mcp_vault_search_entries）
https: {
  pfx: fs.readFileSync('<工作区根目录>/.trae/certs/localhost-dev.pfx'),
  passphrase: '<从本地密码管理器检索 localhost-dev.pfx 口令>',
}
```

- **配套改动（worktree 并行）**：启动端口从 `7153` 起分配（避开主仓库 8080；与主仓库或其它并行 worktree 冲突时递增，如 7154）、`host: '0.0.0.0'`；按联调对象选 proxy target（仅实施期联调用，终验不走本地）：
  - **未改后端 → 直连 UAT 后端环境**：`target: 'https://uat-pms.jomoo.com/pms'`，rewrite 保持 `/^\/service\//`；无需启动本地后端（登录配置与登录链路排查见 `start-pms-backend`「登录链路三跳与账号配置」）
  - **改了后端 → 直连本地**：`target: 'http://localhost:8098'`，rewrite 改 `/^\/service\/pms-service\//`（配合 start-pms-backend）
- **一次性性质（主仓库处理一次即可）**：证书生成/装入系统受信为操作系统级操作（一次永久，与 git 树无关）；证书文件固定归档于 `.trae/certs/` 不随树走（所有树共用）；vite 配置的 pfx 引用提交到分支后新建 worktree 检出即自带——唯一例外是 proxy 本地 target 等联调配置若不入共享分支，每次建树后需本地确认
- **换机注意**：上例证书路径为占位符，实际路径 = 本机工作区根目录 + `.trae/certs/`；更换开发机需重新生成自签证书、装入系统受信根证书颁发机构，新口令同步存入本地密码管理器 MCP，并按新路径同步 vite 配置

## 提交与分支同步 {#提交与分支同步}

- 代码变更与编译构建产物**分别独立提交**
- **提交只发生在 uat**（2026-10-22 用户纠正）：pms 系仓库所有代码提交一律在 uat（worktree 树内或主仓库 uat 分支），dev 只作为 uat 的同步镜像，禁止在 dev 直接提交后反向同步 uat；建树/提交前先 `git branch --show-current` 确认在 uat，主仓库停在 dev 时先切 uat 再操作
- **统一推送原则**：存在多个提交时（代码变更 + dist 产物等），先完成全部本地提交，最后一次 `git push` 统一推送；禁止「提交一个、推送一个」的交替模式
- **合并推送安全闸门**（`--no-ff` 合并、push 前清点待推提交、主分支不积压）→ 统一规则见 `worktree` 技能「合并推送」章节，本 SOP 只引用不重复维护
- 前端 dist：AI 基于最新源码 build → `git add -A dist` 独立提交（与代码提交一起在最后统一推送）（用户不再手动控制）；**时序固定（2026-10-28 用户纠正）：dist 提交必须在 `--no-ff` 合并回主仓库之后、基于合并后源码 build，在主仓库独立提交，禁止在 worktree 树内 build/commit dist**——树内 dist 提交会随 merge 一并带进 uat，产物可能对不上合并后的最终源码；树内已误提时在合并前撤出该 dist 提交，合并后在主仓库重建补交；dist hash 冲突处置见 `worktree` 技能「dist 构建产物冲突统一策略」
- uat→dev：**全量同步、不做筛选**（用户已拍板「dev 需与 uat 完全一致」），**方式固定 cherry-pick、禁止 merge 整个 uat**（2026-10-23 拍板）。流程细则（含 dist 本地重建、环境指向回归）单一来源见 `cherry-pick` 技能，本 SOP 不重复维护
- **整批 cherry-pick 前先看最终差异集**（2026-10-28 实证）：先 `git diff --name-only origin/dev origin/uat` 确认两分支最终内容差异——差异仅本次修复文件时直接单条 cherry-pick 对应提交即可达成一致；`git cherry` 的 patch-id 在分支分叉演化下会误报「已合并」，盲目整批摘取会产生空提交与冲突；批量摘取遇空提交用 `git cherry-pick --skip` 自动跳过，遇冲突先 `--abort` 回到差异集复核，禁止强行续摘
- **同步完成后必须把工作分支切回 uat**（2026-10-28 用户纠正）：uat→dev 同步与推送结束即 `git checkout uat`，`git branch --show-current` 复核；主仓库不得停在 dev——后续提交只发生在 uat，停在 dev 会把下次改动直接提进 dev，破坏「dev 仅为 uat 镜像」的一致性
- 多仓库（SOA 微服务/前端嵌套 git 仓库）场景 cherry-pick 技能支持批量；各仓库各自完成全部本地提交后统一推送
- **字段下线口径同步**：删除/作废字段时全仓检索英文名、中文名与库列名，覆盖前端接入文档与 `docs/business`；被 gitignore 的 `docs/` 也要本地更正（仅本地、不提交）；历史分析类文档（老系统字段梳理）保留原样，不篡改历史事实

| `grill-me` | 需求澄清与方案对齐：决策树追问、用户拍板后实施 | 需求梳理确认、方案设计 |
| `worktree` | 任务隔离：建树 → 树内开发 → 合并 → 推送后回收 | 实施建树、合并提交推送时合并/回收 |
| `test-driven-development` | TDD 循环详细规则：先写失败测试、最小实现、重构纪律 | 实施 |
| `vitest` | 前端 .vue 组件级单测经验（transform 配置、组件依赖链隔离、call 风格模拟、异步断言） | 前端/UI 改动本地单测 |
| `start-pms-backend` | 本地后端启动（java -cp 直跑主类） | 实施调试与本地简化冒烟（改了后端时） |
| `gitlab-operate` | 跟踪 CI 流水线至镜像构建推送完成 | UAT 部署后终验前置 |
| `rancher-ops` | 核对 UAT Pod 启动时间晚于推送时间、确认新镜像生效 | UAT 部署后终验前置、字段物理下线时序 |
| `use-yaak` | 接口测试主手段（HTTP/REST 直调、请求保存复用、认证配置；断点排查法/导出校验/Node fetch 模板见其 examples.md） | E2E 接口层验证 |
| `dbx-database` | 数据库操作（dbx MCP）：查库裁决数据现状 vs 代码缺陷、统计填充率；DDL 经确认后执行；凭据由 DBX 统一管理 | 实施表变更、E2E 异常裁决 |
| 本地密码管理器 MCP（mcp_vault_*） | 检索接口认证、证书口令等密码凭据，禁止硬编码 | 全流程需要密码时 |
| `TRAE-browseruse-external` | UI 层验证主手段（操作用户本机 Chrome，有登录态） | E2E UI 层验证 |
| 电脑控制（trae-remote-official:computer-use） | UI 验证降级手段（Windows UI Automation，可跨应用/系统弹窗/验证码场景） | E2E UI 层验证（浏览器搞不定时） |
| TRAE-code-review | 提交前质量闸门 | 代码评审 |
| `code-organization-review` | 代码组织维度专项评审（分层/职责/接口出口/依赖/命名） | 代码评审 |
| `cherry-pick` | uat→dev 全量同步 | 合并提交推送 |
| `jpm-zentao-operate` | 工时填写、缺陷单/需求/任务关闭 | 禅道条件闭环（有单号时） |
| `learn` | 会话复盘：分析经验教训，固化到全局技能/项目规约文档 | 经验复盘（收尾） |
