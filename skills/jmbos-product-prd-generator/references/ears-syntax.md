# EARS 需求语法规范

EARS (Enhanced Automated Requirements Specification) 是一种结构化的需求编写方法，通过标准化的语法模式确保需求的清晰性、完整性和无歧义性。本文件示例与 PRD 实际生成语言保持一致，全部使用中文。

## EARS 核心语法模式

### 1. 通用需求模式 (Ubiquitous)

无前置条件，系统在任何情况下都应满足的需求。

**语法：** `系统应当 <系统响应>`

**示例：**
- 系统应当要求用户通过身份验证后才能访问敏感数据。
- 系统应当使用 SHA-256 算法加密所有用户密码。
- 系统应当为所有用户操作记录带时间戳的日志。

### 2. 事件驱动模式 (Event-driven)

当特定事件发生时，系统应执行特定响应。

**语法：** `当 <触发事件> 时，系统应当 <系统响应>`

**示例：**
- 当用户点击"提交"按钮时，系统应当校验所有输入字段。
- 当支付交易完成时，系统应当向用户发送确认邮件。
- 当系统检测到未授权访问时，系统应当立即锁定账户。

### 3. 状态驱动模式 (State-driven)

当系统处于特定状态时，应满足特定需求。

**语法：** `当系统处于 <状态> 时，系统应当 <系统响应>`

**示例：**
- 当系统处于维护模式时，系统应当向所有用户显示维护公告。
- 当用户会话空闲超过 30 分钟时，系统应当自动登出用户。

### 4. 可选特性模式 (Optional Feature)

当某功能被使用时，才适用的需求。

**语法：** `如果 <功能被启用>，系统应当 <系统响应>`

**示例：**
- 如果用户启用了双因素认证，系统应当要求密码和验证码同时正确才能登录。
- 如果使用导出功能，系统应当支持 CSV 和 Excel 两种格式。

### 5. 条件异常模式 (Conditional with Exception)

在特定条件下执行某操作，但存在例外情况。

**语法：** `当 <条件> 时，系统应当 <响应>；除非 <异常条件>，此时系统应当 <异常响应>`

**示例：**
- 当用户提交表单时，系统应当校验所有字段；除非用户点击"存为草稿"，此时系统应当跳过校验直接保存。
- 当订单金额超过 10000 元时，系统应当要求经理审批；除非用户具有高级经理角色，此时系统应当自动通过。

### 6. 组合条件模式 (Complex Conditional)

包含多个前置条件的复杂业务规则。

**语法：**
- `当 <条件1> 且 <条件2> 时，系统应当 <系统响应>`
- `当 <条件1> 或 <条件2> 时，系统应当 <系统响应>`

**示例：**
- 当用户已登录且具有管理员角色时，系统应当允许访问用户管理模块。
- 当订单状态为"待处理"或"处理中"时，系统应当允许取消订单。

## EARS 关键字说明（中英对照）

| 中文关键字 | 英文对应 | 含义 | 使用场景 |
|-----------|---------|------|---------|
| 应当 / 必须 | SHALL | 强制性需求 | 默认需求表述 |
| 建议 | SHOULD | 推荐实现，非强制 | 非强制建议 |
| 可以 | MAY | 可选功能 | 可选项 |
| 将要 | WILL | 未来版本需求 | 远期规划 |

> PRD 生成时统一使用中文关键字「应当」「必须」表示强制性需求，避免中英混用。

## 需求编号规则

采用分层编号体系：`REQ-[模块]-[功能点]-[序号]`

**示例：**
- `REQ-SYS-LOGIN-001` - 系统模块-登录功能-第1条需求
- `REQ-CMS-ARTICLE-001` - 内容模块-文章功能-第1条需求

## PRD 功能需求详情中的 EARS 应用

### 功能点 EARS 列表

每个功能点下的"EARS格式需求列表"必须使用 EARS 语法编写。EARS 模式取值：事件驱动 / 条件异常 / 通用需求 / 状态驱动 / 可选特性 / 不需要。

**示例：手机号登录功能**

| 需求ID | 需求描述 | EARS模式 |
|--------|----------|----------|
| REQ-SYS-LOGIN-001 | 当用户输入手机号和密码并点击登录时，系统应当验证凭证并在成功时生成会话令牌 | 事件驱动 |
| REQ-SYS-LOGIN-002 | 当用户连续 5 次输入错误密码时，系统应当锁定账户 15 分钟 | 条件异常 |
| REQ-SYS-LOGIN-003 | 当用户登录成功时，系统应当返回有效期为 30 天的令牌 | 通用需求 |
| REQ-SYS-LOGIN-004 | 如果用户已登录，系统应当自动跳转至首页 | 可选特性 |

### 验收标准部分

验收标准也必须使用 EARS 语法，确保每条标准清晰可测。

**示例：**

| 验收标准ID | 关联功能点ID | 验收条件（EARS格式） | 预期结果 | EARS模式 |
|------------|-------------|---------------------|----------|----------|
| AC-SYS-LOGIN-001 | F-SYS-002 | 当输入正确手机号和密码时，系统应当成功登录并跳转至首页 | 页面跳转至首页，会话令牌写入成功 | 事件驱动 |
| AC-SYS-LOGIN-002 | F-SYS-002 | 当手机号未注册时，系统应当提示"该号码尚未注册" | 提示文案正确显示，无会话生成 | 事件驱动 |
| AC-SYS-LOGIN-003 | F-SYS-002 | 当密码错误时，系统应当提示剩余尝试次数 | 提示"密码错误，剩余 N 次尝试机会" | 事件驱动 |
| AC-SYS-LOGIN-004 | F-SYS-002 | 当连续 5 次密码错误时，账户应当被锁定 15 分钟 | 账户状态变为"锁定"，15 分钟内禁止登录 | 条件异常 |
| AC-SYS-LOGIN-005 | F-SYS-002 | 当登录成功时，令牌有效期应当为 30 天 | 令牌过期时间戳为当前时间+30天 | 通用需求 |

> 验收方法不纳入 PRD 验收标准表，由测试团队根据验收条件自行制定。

## 常见错误与修正

### 错误1：使用自然语言描述而非结构化需求

**错误写法：**
```
用户登录时要验证手机号和密码，验证通过后才能进入首页。
```

**正确写法（EARS）：**
```
当用户提交登录凭证时，系统应当校验手机号和密码，校验通过后系统应当跳转至首页。
```

### 错误2：需求描述包含实现细节

**错误写法：**
```
点击登录按钮后通过 MySQL 查询验证密码，验证通过后跳转至首页。
```

**正确写法（EARS）：**
```
当用户提交登录凭证时，系统应当校验凭证的有效性。
```

### 错误3：需求描述过于模糊

**错误写法：**
```
系统应该安全。
```

**正确写法（EARS）：**
```
系统应当使用 TLS 1.2 或更高版本对所有传输中的敏感数据进行加密。
```

## EARS 需求检查清单

编写完需求后，使用以下检查清单进行自检：

- [ ] 每条需求是否以"系统应当"或"当……时，系统应当"开头
- [ ] 需求是否清晰、具体、可测试
- [ ] 需求是否避免了实现细节
- [ ] 需求是否无歧义
- [ ] 需求是否可追溯（关联到功能点和用户故事）
- [ ] 需求编号是否唯一且符合规则
