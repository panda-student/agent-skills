# Skill 类型对比 {#skill-类型对比}

## 核心区别：user-invocable 和 disable-model-invocation 组合

**这是区分三种 Skill 类型的决定性配置：**

| 类型 | 触发方式 | 调用者 | user-invocable | disable-model-invocation | 适用场景 |
|------|---------|-------|---------------|-------------------------|---------|
| **双模式型** ⭐ | AI自动 + 用户手动 | Claude/用户 | `true` | 不设置 | 通用技能（推荐） |
| **参考型** | AI 自动识别 | Claude | 不设置 | 不设置 | 纯知识规范 |
| **任务型** | AI自动 + 用户手动 | Claude/用户 | `true` | 不设置（敏感操作时设`true`） | 流程编排/操作类 |

> ⚠️ **敏感操作覆盖**：当任务型技能涉及部署/删除/发布等敏感操作时，额外设置 `disable-model-invocation: true`，防止 AI 自动执行。这是**覆盖配置**，不是任务型的固有属性。

## 详细对比

| 特征 | 双模式型 Skill | 参考型 Skill | 任务型 Skill |
|------|---------------|-------------|-------------|
| AI自动调用 | ✅ 是 | ✅ 是 | ✅ 是（敏感操作时可禁用） |
| 用户手动调用 | ✅ 是 (`/命令`) | ❌ 否 | ✅ 是 (`/命令`) |
| 副作用 | 可选 | 无 | 可能有 |
| 权限配置 | 只读或读写 | 只读权限 | 读写权限 |
| 命名规范 | 按功能选择 | 名词+最简词 | 动词+最简词 |
| 推荐度 | ⭐⭐⭐ 推荐 | ⭐⭐ 特定场景 | ⭐⭐ 特定场景 |

## 配置示例

### 双模式型（推荐）
```yaml
---
name: skill-name
description: 功能描述 + 执行方式 + 触发场景
user-invocable: true
allowed-tools:
  - Read
  - Grep
  - Glob
---
```

### 参考型（纯知识）
```yaml
---
name: skill-name
description: 功能描述 + 执行方式 + 触发场景
allowed-tools:
  - Read
  - Grep
  - Glob
---
```

### 任务型（流程编排/操作类）
```yaml
---
name: skill-name
description: 功能描述 + 执行方式 + 触发场景
user-invocable: true
# disable-model-invocation: true  # 取消注释：敏感操作时启用
allowed-tools:
  - Read
  - Write
  - Edit
  - Bash
---
```

# Skill 类型自动判断 {#skill-类型自动判断}

## 判断原理

基于用户描述的功能关键词，自动识别 Skill 类型：

**核心判断逻辑**：
- 描述包含"执行动作产生结果"→ **任务型**
- 描述包含"提供知识指导决策"→ **参考型**
- 默认 → **双模式型**（大多数技能）

## 关键词分类

### 任务型关键词（动词导向）

| 关键词分类 | 具体词汇 | 典型场景 |
|-----------|---------|---------|
| **创建类** | 创建、生成、构建、编写、制作 | 产生新内容 |
| **执行类** | 部署、运行、执行、启动、发布 | 执行操作 |
| **变更类** | 修改、更新、删除、重构、迁移 | 变更操作 |
| **检查类** | 检查、测试、审查、验证、诊断 | 质量操作 |
| **配置类** | 安装、配置、初始化、设置 | 环境操作 |

### 参考型关键词（名词导向）

| 关键词分类 | 具体词汇 | 典型场景 |
|-----------|---------|---------|
| **规范类** | 规范、标准、规则、约定、准则 | 约束性知识 |
| **指导类** | 指南、流程、架构、模式、策略 | 指导性知识 |
| **风格类** | 风格、惯例、最佳实践、约定 | 经验性知识 |

## 判断流程

```
用户描述 → 提取关键词
    ↓
包含任务型关键词？ ──是──→ 任务型
    ↓否
包含参考型关键词？ ──是──→ 参考型
    ↓否
双模式型（默认）
```

## 边界情况处理

- **混合型描述**：优先根据**主要目的**判断
  - "创建一个组件生成器，遵循项目规范" → 任务型（主要目的是生成组件）
  - "定义API规范，并提供示例代码生成" → 参考型（主要目的是提供规范）
- **模糊描述**：根据**预期触发方式**判断
  - 需要用户主动调用 → 任务型
  - 需要自动触发提供参考 → 参考型

# Description 编写公式 {#description-编写公式}

**标准公式**：`功能描述 + 执行方式 + 触发场景`

## 优化原则：提高自动触发概率

### 关键词覆盖策略
- **同义词覆盖**：包含多个同义词，提高匹配概率
- **场景关键词**：描述用户可能的使用场景

### 触发时机关键词
- 参考型：明确说明何时自动触发
- 任务型：明确说明通过斜杠命令触发

## 示例对比

### 参考型
- ✅ `定义项目 RESTful API 设计规范，包含URL命名、响应格式、状态码与鉴权规则，在编写/审查接口、设计新API、确定请求响应格式时自动使用`
- ❌ `API 规范`（过于简单，触发概率低）

### 任务型
- ✅ `创建符合项目规范的 React 组件，通过斜杠命令触发，用于快速生成标准化组件代码`
- ❌ `创建组件`（过于简单）

# 上下文注入配置 {#上下文注入配置}

## 概述

上下文注入（Context Injection）允许在 Skill 加载时预执行命令并注入上下文。

## 配置格式

```yaml
context-injection:
  - name: context-name        # 上下文标识符（唯一）
    command: shell-command    # 要执行的命令
    description: 用途说明      # 该上下文的用途描述
```

## 设计原则

- **相关性**：注入的上下文应与 Skill 的知识领域直接相关
- **轻量化**：命令输出应保持简洁，避免大量输出消耗 Token
- **容错性**：命令应具备容错能力，避免因环境差异导致加载失败
- **安全性**：避免注入敏感信息，对敏感数据进行脱敏处理

```yaml
# ✅ 正确：提供默认值
context-injection:
  - name: lint-config
    command: cat .eslintrc.* 2>/dev/null || echo "No lint config"
    description: lint 配置
```

# 目录结构标准 {#目录结构标准}

> **路径基准说明**：`~/.agents/skills/` 为技能实际安装位置，`~/.claude/skills/` 是指向它的符号链接，两者内容同步。以下结构对任一位置均适用，以 `.claude/skills/` 为例展示（路径关系与符号链接操作见 [重命名流程](#重命名流程)）。

```
.claude/skills/
├── [skill-name]/
│   ├── SKILL.md          # 主入口文件（必需，行数规范见最佳实践建议）
│   ├── reference.md      # 参考文档（可选）
│   ├── examples.md       # 示例文档（可选）
│   ├── scripts/          # 可执行脚本（可选，自包含原则）
│   ├── bin/              # 小型工具/二进制（可选，自包含原则）
│   ├── data/             # 数据文件（可选，自包含原则）
│   ├── theories/         # 理论文件（可选）
│   └── templates/        # 模板文件（可选）
```

## 文件职责（遵循单一职责原则）
- **SKILL.md**：智能路由器，只负责路由和核心提示
- **reference.md**：详细规范，只负责规范说明
- **examples.md**：示例文档，只负责示例展示
- **theories/**：理论文件，只负责理论阐述
- **templates/**：模板文件，只负责模板定义

# 最佳实践建议 {#最佳实践建议}

- **渐进式披露**：SKILL.md 定位为智能路由器，只包含核心提示和路由表
- **单一职责**：每个文件只负责一个明确的功能领域。**反模式**：改一条规则要改 N 个文件 → 碎片化过度，应合并
- **依赖抽象**：技能依赖功能接口而非具体技能名称，详见 [核心原则](./theories/principles.md)
- **自包含**：技能应尽可能自包含，小型脚本、执行文件、配置文件等应包尽包，详见 [核心原则](./theories/principles.md)
- **禁用编号**：技能内容不使用任何编号，详见 [编号禁用规则](#编号禁用规则)
- **最小权限**：精确授权到子命令，不使用 `Bash(*))`
- **合理拆分**：高频核心语义 → SKILL.md（内联），低频细节/示例/数据 → reference.md/examples.md（外置），核心理论 → theories/，可复用模板 → templates/
- **行数规范**：SKILL.md ≤150行内容直接写，>150行升级为纯路由
- **定期维护**：随着项目发展，及时更新 Skill 内容以保持其有效性

# 编号禁用规则 {#编号禁用规则}

## 规则

**技能内容一律不使用编号**：创建技能时直接不写编号；优化/审查技能时发现编号一律移除。

❌ 禁用形式：

- 有序列表：`1.` `2.` `3.`
- 编号标题：`### 1. xxx`、`## 一、xxx`
- 编号步骤：`步骤 1`、`Step 1`、`第 N 步`
- 编号示例：`示例 1`、`错误 1`

## 原因

技能内容会被反复修改（增删条目、调整顺序），编号随之错位：

- 插入/删除条目后需全文重新编号，漏改即产生编号错误
- 交叉引用编号（如"见步骤 3"）在错位后指向错误内容

## 替代方式

| 需求 | 替代方案 |
|------|---------|
| 并列条目 | 无序列表 `-` |
| 顺序/流程 | 箭头 `A → B → C`，顺序由上下位置表达 |
| 层级结构 | 多级标题（不带序号） |
| 多项对照 | 表格 |

## 执行时机

- **创建技能**：生成内容时直接使用无序列表/标题/箭头，不写编号
- **优化/审查技能**：扫描所有技能文件（SKILL.md、reference.md、examples.md、theories/、templates/），发现编号即移除并改为替代方式

# 重叠处理规则 {#重叠处理规则}

## 处理方式决策

技能内容或功能重叠时，**先判断合并还是提取**，不可默认合并：

| 判断维度 | → 合并 | → 提取 |
|---------|-------|-------|
| 重叠范围 | 整体重叠，功能范围/触发场景基本一致 | 局部重叠，仅共享部分内容或能力 |
| 独立职责 | 职责无法拆分，拆开反而割裂流程 | 各自有独立职责与触发场景 |
| 演进方向 | 后续始终一起修改 | 两边独立演进，重叠部分变化节奏不同 |
| 用户视角 | 对使用者是同一件事 | 对使用者是两个不同能力 |

## 合并流程（高度重叠）

- 识别重叠 → 对比两个技能的功能范围
- 判断保留 → 保留覆盖面更广的技能
- 合并内容 → 将被移除技能的独特内容合并到保留技能
- 移除冗余 → 删除被移除技能的目录（~/.agents/skills/ 和 ~/.claude/skills/）

## 合并原则

被合并技能的内容按类型归入目标技能：

| 内容类型 | 合并目标 |
|---------|----------|
| API操作类 | jpm-api |
| 架构知识类 | jpm-architecture |
| 业务规则类 | jpm-business |
| 通用工具类 | 保留功能更全的 |

## 提取流程（局部重叠）

- 识别重叠 → 定位两个技能共享的内容或能力
- 提取独立 → 重叠部分提取为独立技能：纯规范提取为参考型技能，可执行动作封装为双模式型/任务型技能
- 改造引用 → 原技能删除重复内容，遵循 [依赖抽象原则](./theories/principles.md#依赖抽象原则) 按功能接口引用新技能，不写死技能名称
- 验证回归 → 确认原技能职责完整、新技能可独立触发、相关路由表已更新

## 提取判断标准

- ✅ 提取后新技能有明确、可描述的单一职责
- ✅ 至少两个技能需要该内容（不为单一技能过度拆分）
- ❌ 重叠只是措辞相似、实质内容不同 → 不处理
- ❌ 提取后原技能失去完整流程、强耦合新技能才能跑通 → 改为合并

## 检测方法

- 对比技能 description 与功能描述
- 检查是否有技能功能描述高度相似
- 评估重叠范围（整体/局部）→ 整体重叠选合并，局部重叠选提取

# 重命名流程 {#重命名流程}

### 适用场景

当需要更改技能的名称时，需同步更新多处配置。

### 推荐执行顺序

```
重命名技能目录
  - mv ~/.agents/skills/old-name ~/.agents/skills/new-name

修改 SKILL.md frontmatter
  - 更新 name 字段
  - 更新 description 中的命令引用（如 /old-name → /new-name）
  - 使用 Edit replace_all=true 替换文件中所有旧名称引用

重命名脚本文件（如有）
  - mv old-name.mjs new-name.mjs
  - 更新 SKILL.md 中对脚本文件的引用

更新符号链接
  - rm -f ~/.claude/skills/old-name
  - ln -sf ~/.agents/skills/new-name ~/.claude/skills/new-name

验证测试
  - 检查符号链接是否正确
  - 测试 /new-name 命令是否可用
```

### 避坑提醒

- 符号链接指向错误会导致技能无法加载

---

## 技能仓库维护

- `~/.agents` 本身就是技能仓库：更新直接在该目录 `git pull --rebase` / commit / push，没有额外的 checkout 或同步步骤
- `~/.claude/skills` 是指向 `~/.agents/skills` 的目录 junction；对 junction 下的路径严禁 `Remove-Item -Recurse -Force`，否则删除的是真身（2026-11-06 实证：整目录被删）
- `skills/*` 默认被 `.gitignore` 忽略；新增技能需在白名单加 `!skills/<name>/` 才会纳入版本管理
- 从远端同步技能目录用 `robocopy <repo>\skills ~/.agents\skills /E`，不要 `/MIR`（会删掉本地独有技能）
- push 遇 `OpenSSL SSL_read: unexpected eof` 时加代理：`git -c http.proxy=http://127.0.0.1:7892 push origin main`
- 修改技能 name/description 后同步 cc-switch 数据库（见 `cc-switch-sync` 技能）

触发方式：AI 自动调用 + 用户手动调用
确认或调整：A.确认双模式型  B.切换为参考型  C.切换为任务型

- 类型判断逻辑 → [Skill 类型自动判断](#skill-类型自动判断)

**输出**：确认的 Skill 类型

### 确认命名

系统根据功能建议命名，你确认或修改

**命名规则**：[命名规则](#命名规则)
- 参考型：名词+最简词（如 `api-rule`、`style-guide`）
- 任务型：动词+最简词（如 `make-component`、`deploy-app`）
- 双模式型：按主要功能选择动名词

**输出**：确认的技能名称

### 生成文件

**执行步骤**：
- 使用 [统一模板](./templates/unified-skill-template.md) 生成 SKILL.md
- 根据类型配置 frontmatter（参考 [类型对比](#skill-类型对比)）
- 编写 description（参考 [Description 编写公式](#description-编写公式)）
- 配置 allowed-tools（参考 [权限控制配置](#权限控制配置)）
- 创建 reference.md（详细规范）、examples.md（示例）等可选文件
- **编号检查**：内容不使用编号，用无序列表/标题/箭头表达顺序（规则见 [编号禁用规则](#编号禁用规则)）
- **自包含检查**：扫描技能中引用的所有脚本/文件/路径，能内包的放入技能目录内（scripts/、bin/、data/），仅允许系统级运行时（git、node、python）作为外部依赖

**输出**：完整的技能文件和目录结构

# 优化流程 {#优化流程}

### Skill 诊断

**输入**：技能目录路径

**执行步骤**：
- 读取所有技能文件（SKILL.md、reference.md、examples.md、theories/、templates/）
- 使用 [测试清单](./theories/skill-test-checklist.md) 逐项检查
- **编号诊断**：扫描所有技能文件中的编号（有序列表、编号标题、步骤 N、示例 N），发现即列为问题（规则见 [编号禁用规则](#编号禁用规则)）
- **自包含诊断**：扫描技能中所有外部路径引用（绝对路径、其他技能目录引用），评估是否应内包
- **SSOT 诊断**：检查同一规则是否在多个文件中重复定义
- **重叠诊断**：检测与其他技能的内容/功能重叠，按 [重叠处理规则](#重叠处理规则) 决策合并或提取
- **单一职责诊断**：逐文件检查职责是否单一（文件名反映内容、内容聚焦单一主题、修改原因唯一），技能整体无跨领域功能混杂（规则见 [单一职责原则](./theories/principles.md#单一职责原则)）
- **路由诊断**：验证路由表是否覆盖所有主要功能和资源

**输出**：诊断报告（问题列表，按严重程度排序：❌严重 → ⚠️中等 → 💡低等）

### 优化建议

**输入**：诊断报告

**执行步骤**：
- 对每个问题提出具体修复方案
- 参考 [最佳实践建议](#最佳实践建议) 和 [核心原则](./theories/principles.md)
- 评估修复优先级（严重问题必须修复，低等问题可延后）
- 与用户确认优化范围

**输出**：优化方案（问题→修复方案→优先级）

### 重构实施

**输入**：确认的优化方案

**执行步骤**：
- 按优先级从高到低执行修复
- 移除内容中的编号并改为替代方式（规则见 [编号禁用规则](#编号禁用规则)）
- 每次修改后验证文件格式正确（frontmatter 完整、链接有效）
- 遵循 [核心原则](./theories/principles.md)：不违反渐进式披露、单一职责、SSOT

**输出**：修改后的文件

### 验证测试

**输入**：修改后的文件

**执行步骤**：
- 重新运行 [测试清单](./theories/skill-test-checklist.md) 验证
- 确认所有严重问题已修复
- 确认修复未引入新问题
- 生成测试报告

**脚本能力扩展的补充规则**（技能内含解析脚本/命令行工具时，检查项见清单「脚本能力扩展验证」节）：

- 新增解析能力必须三件套同步：解析（parsers）+ 渲染（renderers）+ 夹具样本与用例进快照——缺夹具样本则快照保护为空，未来改动会静默弄坏新能力
- 能力清单/覆盖矩阵的每项标签分类需有实证样例支撑，无实证标注「待验证」——分类错误会产生能力盲区（工具永不解析、梳理永远漏且无告警）
- 新夹具样本会涟漪影响全局扫描类用例（refs/locate 等全库检索的命中数），属预期变更，baseline 刷新对应模块即可

**输出**：验证结果 + 测试报告
